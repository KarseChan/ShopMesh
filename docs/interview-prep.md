## §1 架构与「确定性 vs LLM」边界(核心主攻)

### Q1. 为什么砍掉 LLM 动态 DAG 编排?什么场景你会保留它?
- **考点**:是不是为收敛而收敛;有没有 tradeoff 判断。
- **答**:导购意图空间**封闭已知**(搜/推、详情/比价、澄清、下单)→ 确定性 if/else 路由就够。LLM 动态拆 DAG 换来的灵活性用不上,却引入:①每次多一发 LLM(慢、贵)②JSON 解析失败点 ③环检测/拓扑排序复杂度 ④0 测试、出过循环 bug。收益<成本 → 砍。
- **什么时候保留**:意图**开放/长尾**、步骤**因输入而异且不可枚举**(如通用 Agent、复杂科研/运维任务),或需要**动态并行 fan-out** 且子任务边界事前未知时,DAG 才有价值。
- **追问「那你不就退回到硬编码工作流了?」**:是——但对封闭域这正是对的;我保留了 ReAct 在**工具选择**层的灵活(agent 自己决定调哪个工具、调几次),只是**编排骨架**确定化。灵活性放在该放的层。

### Q2. "毫秒级 feed 不能塞 LLM"——凭什么?生产上真这样吗?
- **考点**:核心 thesis 是真懂还是话术。
- **答**:①**延迟**:feed 是高 QPS、P99 要几十 ms;单次 LLM 推理 7–15s(我的网关实测),差 3 个数量级,物理上进不了在线路。②**产业印证**:淘宝 RecGPT 是"LLM 离线富化 + 传统召回在线毫秒服务";美团 2025「小美」LLM 只在**对话层**,feed 仍是级联 recsys。③**我的落地**:秒送里就近召回/硬过滤/排序全确定性,LLM 只在"对话式凑单"这种能容忍秒级、且多步权衡有增量的地方。
- **追问「那 LLM 在推荐里到底该干嘛?」**:离线做**特征富化/语义标签/冷启动内容理解**,在线做**对话式意图澄清与编排**;排序打分仍是轻量模型。
- **深水**:能引 RecGPT / 级联架构(召回→粗排→精排→重排)说明你懂 recsys 分层,这题就满分。

### Q3. 三层管线(Preprocessing / Agent Execution / Postprocessing)为什么这么切?
- **答**:把**低风险、可确定化**的放前后(preprocess:意图分类+实体抽取+记忆召回并行;postprocess:记忆写入+偏好抽取,fire-and-forget 不阻塞响应),中间只留**必须推理**的 ReAct。好处:①并行降延迟 ②确定性部分可测、可缓存、可规则快路径 ③LLM 上下文干净(只喂它需要的)。
- **追问「preprocess 并行具体并了什么?」**:意图(语义路由)、实体、记忆召回三路 `asyncio.gather`;首轮简单 query 走**规则快路径**跳过 embedding 和 LLM。

## §2 延迟优化(我一定追 22s)

### Q4. 116s→22s 怎么定位的?根因?为什么不直接换模型?22s 还是很慢啊。
- **考点**:是不是拍脑袋优化;懂不懂天花板。
- **答**:①**实测**:profiler 拆出 116s = 8 次串行 LLM(抽实体 20s + agent 迭代 + 逐商品文案 47s + 总结 14s)。②**根因**:网关只有一个慢推理模型,**换不了模型→只能减调用次数**。③**手段**(对照生产"离线富化"原理):逐商品文案改用排序器的**确定性理由**(去 3 次)、总结**模板化**(去 1 次)、**规则快路径**抽实体(20s→2.6s)、收敛冗余工具调用 → 8 次降到 1–2 次。
- **"22s 还是慢"(必答好)**:诚实——22s 的地板是**基建**:单次推理模型 7–15s + bge-m3 **CPU embedding ~9s**。架构上我已经把调用次数压到近极限;要再降是**基建活**:换更快的模型/GPU embedding/小 embedding 模型,或把 embedding 也移出在线路(缓存/预计算)。**我优化的是架构可控的部分,并诚实标注了物理地板在哪。** 这比报一个漂亮数字更重要。
- **追问「哪 1–2 次 LLM 还留着?为什么去不掉?」**:一次 agent 决策(选工具/组织回答),必要;偶尔一次澄清。其余全确定化了。

### Q5. 规则快路径抽实体——抽错了怎么办?准确率怎么保证?
- **答**:**保守原则,宁可回退不降准**:必须命中 searchable anchor(product_type / 高置信 category),去 token+停用词后残留描述性内容过多→判定"不简单"→**返回 None 回退 LLM**。礼物/场景类天然无 anchor→回退。所以快路径只吃"简单常见"query,错的成本是"回退多花一次 LLM",不是"抽错"。

## §3 交易系统(后端深水区,我会往死里追并发)

### Q6. 库存防超卖怎么做?为什么 Redis 不用 DB 行锁?
- **答**:Redis `DECRBY` **原子**扣减,返回值 <0 就 `INCRBY` 回滚 → 天然无锁防超卖(单线程原子)。不用 DB 行锁:①行锁在高并发下是热点、吞吐差 ②库存是典型**高频读写、可最终落库**的场景,Redis 内存操作快几个量级。
- **追问「Redis 挂了库存丢了怎么办?」**:①seed 用 `SET NX` 从商品 JSON 初始化,可重建 ②生产上 Redis 持久化(AOF)+ 定期与 DB 对账 ③这是 mock,真实场景库存是独立库存服务。
- **深水「多个 item 部分扣成功怎么办?」**:逐个 reserve,任一失败**回滚已占的**(补偿),返回库存不足。

### Q7.(必被问)下单要 Redis 扣库存 + PG 落订单,这俩不是一个事务,一致性怎么保证?
- **考点**:分布式事务/最终一致性认知。**这是我埋的坑,你必须答好。**
- **诚实答**:确实**不是**跨 Redis+PG 的原子事务,是**补偿式(saga-lite)**:先 reserve 库存 → 落库,**落库失败则 catch 后 release 库存**。
- **主动暴露缺口**(加分):`reserve 成功→进程硬崩→没走到 release` 的窗口会**泄漏一个预占**。当前靠 `except` 只能补偿"被捕获的失败",硬崩兜不住。
- **生产我会怎么补**:①**对账/清扫任务**(已有超时未支付订单对账的雏形,可扩成库存预占对账)②**outbox / 事务消息**保证"落单"与"扣减"最终一致 ③或把库存扣减做成"下单成功后异步确认、超时释放"。**知道自己方案的边界 + 说得出生产级补法,是这题的满分。**

### Q8. 幂等键怎么设计?两个请求拿同一个 key 并发下单会怎样?
- **答**:`idempotency_key` 建**唯一索引**;下单先按 key 查已存在→直接返回同一单。
- **诚实并发缺口**:两个并发同 key 都"查无"→都 insert→唯一索引让第二个**报错**→当前被 catch 成"下单失败"并 release。**正确做法**:第二个应捕获唯一冲突后**查出并返回已存在的订单**(而非报失败)。这是我知道要改的点。
- **key 谁生成**:客户端生成(如 `idem-{uid}-{ts}`),防的是**网络重试/重复提交**导致重复扣款。

### Q9. 支付为什么"只信 webhook"?验签怎么做?重复回调?
- **答**:①**红线**:前端可被篡改,订单转 `paid` **绝不能由前端触发**,只信支付方服务器**异步 webhook**。②**验签**:HMAC-SHA256(共享密钥对 body 签名)+ `hmac.compare_digest` 常量时间比较防时序攻击;**伪造回调实测被拒**。③**幂等**:webhook 可能重复投递,支付会话状态标 `succeeded`,重复回调直接返回、不二次 `mark_paid`。
- **追问「为什么不用非对称签名/为什么 HMAC?」**:HMAC 适合你我共享密钥的场景,简单够用;真实支付网关多用 RSA/证书验签,链路一样(验签→幂等落单),我用沙箱走了**和真实一样的验签链路**。

### Q10. Celery 超时对账为什么需要?消息队列的投递语义?任务重复执行怎么办?
- **答**:①用户下单未付会**占着库存**,需超时(15min)自动取消+释放 → Beat 定时扫 `awaiting_payment` 且超时的单。②MQ 是 **at-least-once**(可能重复投递)→ 任务必须**幂等**(取消已取消的单是 no-op;状态机转移有前置状态校验)。③秒送履约自动推进同理复用这个"定时扫描+状态转移"范式。
- **追问「为什么用 RabbitMQ 不用 Redis 做队列?」**(诚实):对当前规模 **RabbitMQ 偏重、是过度设计**,Redis/Celery 直连就够;当初为"多团队/异步解耦"上的,重来会先简后繁。

## §4 混合检索 / RAG(算法+工程)

### Q11. HNSW 内联过滤 vs 先 Top-K 再过滤,差别?为什么后过滤掉召回?
- **答**:后过滤 = 先取 Top-K 最相似,**再**用条件筛 → 若 Top-K 里满足条件的少,结果就空/少(**召回漏斗塌陷**,实测 FAISS 路 40–70%)。内联过滤 = HNSW 遍历时**只走满足 payload 条件的点** → 返回的 K 个都是"可行且最相似",召回接近 100%。
- **追问「内联过滤会不会破坏 HNSW 图连通性、变慢?」**:会有影响(过滤太狠时图上可行点稀疏,要遍历更多)——Qdrant 用 payload 索引 + 可调策略缓解;这是"召回质量 vs 速度"的权衡,对我这规模召回质量优先。
- **HNSW 一句话原理**:多层可导航小世界图,上层稀疏跳远、下层稠密精找,近似最近邻,查询 ~O(log N)。

### Q12. 每个门店配送半径不同,向量库一个 GeoRadius 怎么按店过滤?
- **考点**:这是秒送里真实的工程细节,能答说明是你做的。
- **答**:单个 `GeoRadius` 只能表达"以用户为心、**一个**半径"——无法表达"每店各自半径"。所以:**粗筛下推**(用最大可能配送半径,如 6km,让 HNSW 先剪掉明显够不着的)+ **精确后过滤**(haversine 逐店 `距离 ≤ 该店 delivery_radius_km`)。粗+精两段,既享受下推剪枝、又保证每店半径正确。
- **同理**:营业中是 `open_hour ≤ now < close_hour` 两个 Range 下推(**真时间**,非静态 baked);时效/预算是 Range 下推。

### Q13. Reranker 现在开着吗?什么时候触发?BGE reranker 原理?
- **诚实答**:**默认关**(config `enabled:false`)——FlagEmbedding 未装,且开着每次查询失败重试白等 ~3s。设计上是**条件触发**(query 模糊/多软需求/候选分数太接近/多品类混排时才启)、**可插拔**。
- **原理**:双塔 embedding(bi-encoder)召回快但精度有限;cross-encoder reranker 把 (query, doc) 拼一起过一遍模型,精度高但慢 → 只对 Top-K 精排。BGE-reranker-v2-m3 就是这种 cross-encoder。
- **被问穿不慌**:"我把它做成可插拔+条件触发,当前为控延迟默认关;架构位置留好了,装上依赖即可启。" 诚实且显示你懂 bi/cross-encoder 分工。

## §5 记忆 / 上下文工程

### Q14. 四层记忆各解决什么?为什么要这么多层?
- **答**:L1 进程工作记忆(单次执行内);L2a Redis 会话滑动窗口(近 5 轮,快)+ 摘要(超限 LLM 压缩);L2c Qdrant 长期向量记忆(跨会话语义召回);L3 PG 用户画像(结构化偏好:品类/价格 EMA/品牌)。**分层理由**:时效性 × 结构化程度不同——短期要快(Redis)、长期要可语义检索(向量)、稳定偏好要结构化可查(PG)。
- **追问「不会不一致吗?」**:各层职责不重叠(工作/会话/长期/画像),写入方向单一;偏好抽取是**后处理异步**批量固化到画像,避免在线路写。

### Q15. Token -30% 怎么测的?哪层省的?
- **诚实答**:对比"朴素全量塞历史" vs "按需召回+预算裁剪"的单次交互 prompt token。省在:①只喂**最后一条 user + 必要工具观测**(不塞全历史)②旧 tool_result 换占位符/持久化到 Redis ③超限才 LLM 摘要。**如果我没有严格 A/B,就说"量级约 30%,基于典型多轮 case 的估算",别编精确实验。**

### Q16. 为什么"读时"衰减而不是写时?
- **答**:写时衰减要定期扫全量更新分数(贵、有写放大);读时衰减 = 召回时按 `now - created` 现算时间衰减因子,**零额外写**、且总是反映当前时刻。经典"惰性计算"权衡。

## §6 多轮 / 状态机 / LangGraph

### Q17. Checkpointer 怎么恢复中断?存哪?并发多轮会串吗?
- **答**:LangGraph 每个节点后把 State 快照存 checkpointer(按 `thread_id` 隔离,一会话一 thread);中断(如 HITL `interrupt()` 等确认)后,用 `Command(resume=...)` 从断点续跑。并发不同会话 thread_id 不同→天然隔离;同会话串行。
- **追问「State 里存什么、不存什么?」**:只存**工作记忆**(意图/实体/检索结果/迭代计数);**执行日志走 structlog 不进 State**(否则 State 膨胀、reducer 混乱)。
- **HITL**:prepare_order → `interrupt("请确认")` → 前端 resume(confirm/cancel)→ 确定性 commit。**LLM 不自主下单**的落地机制。

## §7 系统设计延伸(白板题,考架构 sense)

### Q18. QPS 10 → 1万,先崩哪?怎么改?
- 先崩:①单一慢 LLM 网关(串行、无并发预算)②bge-m3 CPU embedding ③Qdrant 单点 ④Redis/PG 连接。
- 改:LLM 走**离线富化 + 在线轻量**(把生成移出在线路,只留必要澄清);embedding **GPU/批处理/缓存/小模型**;Qdrant **分片+副本**;引入**多级缓存**(热门 query/门店结果);**限流+降级**(agent 不可用时退确定性检索)。核心还是那句:**把能确定化/预计算的都移出在线路**。

### Q19. 扩到多城市、百万门店,geo 检索怎么扩?
- geohash / S2 分区 + 按城市/网格分片;粗召回下推地理网格,精排 haversine;门店索引按城市 collection 隔离;冷热分离。

### Q20. 让这 agent 真上线服务真实用户,还差什么?
- 真实库存/履约系统对接、真实支付网关、可观测(trace/指标/告警,已有 cost tracking 雏形)、更快的模型基建、A/B 与线上指标闭环、权限与多租户隔离加固、prompt 注入的红队测试。
