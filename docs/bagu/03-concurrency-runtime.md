# §A 通用并发原理(所有语言都问)

## 1. 线程安全三要素(必考)
- **原子性**:操作不可分割(如 `i++` 其实是读-改-写三步,非原子)。
- **可见性**:一个线程改了,别的线程能立刻看到(多核有 CPU 缓存,不刷主存就看不到)。
- **有序性**:代码不被(编译器/CPU)重排到出错。
> 并发 bug 基本都是这三者之一被破坏。

## 2. 悲观锁 vs 乐观锁
- **悲观锁**:先加锁再操作(synchronized、DB 行锁、`for update`)。适合写多、冲突频繁。
- **乐观锁**:不加锁,提交时检查有没有被改(**CAS** / 版本号 / DB `where version=x`)。适合读多写少。
- **CAS(Compare-And-Swap)**:`if 内存值==预期 then 改为新值`,由 CPU 指令保证原子。自旋重试。
- **CAS 三大问题**:①**ABA**(值从 A→B→A,CAS 以为没变)→ 加**版本号**;②**自旋开销**(一直失败空转)③**只能保证一个变量**原子。

## 3. 死锁(并发版)
四条件同 OS。编码避免:**按固定全局顺序获取多把锁**、用 `tryLock` 带超时、减少锁持有时间。

## 4. 线程池(必考,后端核心)
- **为什么用**:①复用线程省创建/销毁开销 ②控制并发数防资源耗尽 ③统一管理(监控/拒绝)。
- **核心参数(以 Java ThreadPoolExecutor 七参数为模板,通用适用)**:
  - `corePoolSize` 核心线程数、`maximumPoolSize` 最大线程数、`keepAliveTime` 空闲回收时间、`workQueue` 任务队列、`threadFactory`、`handler` 拒绝策略。
- **执行流程**:核心线程没满 → 建核心线程;满了 → 进队列;队列满 → 建到 max;再满 → **拒绝策略**。
- **拒绝策略**:AbortPolicy(抛异常,默认)、CallerRunsPolicy(调用者线程自己跑,降速反压)、DiscardPolicy(丢)、DiscardOldestPolicy(丢最老)。
- **队列**:有界(推荐,防 OOM)vs 无界(任务堆积风险)。**面试爱问「参数怎么定」**:CPU 密集 ≈ 核数+1;IO 密集 ≈ 核数×(1+等待/计算)或经验值 2×核数;结合压测。

## 5. 生产者-消费者
用阻塞队列解耦:生产者放、消费者取,队列满/空时阻塞。削峰、解耦、异步。MQ 就是分布式版本。

# §B Java 运行时(投 Java 岗必看)

## B1. JMM(Java 内存模型)
- 主内存 + 每线程工作内存(缓存),带来可见性问题。
- **volatile**:①保证**可见性**(写立即刷主存、读从主存)②禁止**指令重排**(内存屏障)。**不保证原子性**(`volatile i++` 仍不安全)。
- **synchronized**:互斥 + 可见性 + 有序;可重入;锁升级(偏向→轻量级(CAS 自旋)→重量级(OS 互斥))。锁对象/类/方法。
- **happens-before**:一组规则,前操作结果对后操作可见(程序顺序、锁、volatile 写读、传递性…)。

## B2. JUC 常用
- **Lock/ReentrantLock**:比 synchronized 灵活(可中断、公平锁、tryLock、多条件 Condition)。
- **AQS(AbstractQueuedSynchronizer)**:JUC 基石;一个 `state` + CLH 双向等待队列;ReentrantLock/CountDownLatch/Semaphore 都基于它。
- **ConcurrentHashMap**:1.7 分段锁 Segment;**1.8 改为 CAS + synchronized 锁单个桶头节点** + 红黑树,粒度更细。
- 原子类 `AtomicInteger`(CAS)、`LongAdder`(分段累加,高并发更强)。

## B3. JVM 内存区域
- **线程私有**:程序计数器、虚拟机栈(栈帧:局部变量表/操作数栈)、本地方法栈。
- **线程共享**:**堆**(对象,GC 主战场,分新生代 Eden+S0+S1 / 老年代)、**方法区/元空间**(类信息、常量池;1.8 后元空间用本地内存)。
- 常见 OOM:堆(对象太多)、栈(递归太深 StackOverflow)、元空间(类太多)。

## B4. GC(垃圾回收)
- **判活:可达性分析**(从 GC Roots——栈引用/静态/常量等——可达即存活;不用引用计数因为解决不了循环引用)。
- **算法**:标记-清除(碎片)、标记-复制(新生代,浪费一半空间但无碎片)、标记-整理(老年代)。
- **分代**:新生代 Minor GC 频繁(复制);对象熬过多次进老年代;老年代 Full GC 慢。
- **收集器**:CMS(并发标记清除,低停顿,有碎片,已废弃)、**G1**(分 Region,可预测停顿,默认)、**ZGC/Shenandoah**(超低停顿,染色指针)。
- **STW(Stop-The-World)**:GC 时暂停业务线程,优化目标就是缩短 STW。

## B5. 类加载
- 过程:加载→验证→准备(静态变量默认值)→解析→初始化。
- **双亲委派**:类加载请求先交父加载器(Bootstrap→Extension→Application),父加载不了才自己加载。**为什么**:防止核心类被篡改(你写个 `java.lang.String` 加载不了)、避免重复加载。打破它:SPI、Tomcat 隔离 webapp。

# §C Python 运行时(投 Python/LLM 岗必看,贴合本项目)

## C1. GIL(全局解释器锁,必考)
- **是什么**:CPython 解释器的一把全局锁,**同一时刻只有一个线程执行 Python 字节码**。
- **为什么有**:CPython 内存管理(引用计数)非线程安全,GIL 简化实现、单线程性能好。
- **影响**:**多线程做 CPU 密集无法利用多核**(线程轮流拿 GIL);IO 密集没事(等 IO 时释放 GIL)。
- **绕过**:①**多进程 multiprocessing**(每进程独立解释器+GIL,真并行,适合 CPU 密集)②C 扩展里释放 GIL(numpy)③换解释器(PyPy 也有,Jython 无)。
- **面试金句**:"我的 Agent 是 **IO 密集**(等 LLM/向量库/DB),GIL 不构成瓶颈,用 **asyncio** 单线程事件循环并发上千 IO 就够;真遇 CPU 密集我会上多进程或 C 扩展。"

## C2. asyncio / 协程
- **事件循环(event loop)**:单线程,遇到 `await`(IO)就挂起当前协程、切去跑别的,IO 就绪再回来。**协作式调度**(不像线程抢占)。
- `async def` 定义协程,`await` 让出控制权;`asyncio.gather` 并发多个。
- 适合**高并发 IO**;CPU 密集会**阻塞事件循环**(要丢线程池/进程池 `run_in_executor`)。
- 你项目:`asyncio.gather` 并行跑意图/实体/记忆召回;同步的 embedding 用 `asyncio.to_thread` 包,避免阻塞循环。

## C3. 内存管理 & GC
- **引用计数为主**:对象引用数归 0 立即回收(及时、简单)。
- **缺陷:循环引用**(A 引 B、B 引 A,计数不为 0)→ **分代 GC** 辅助(三代,定期扫描找不可达的循环)。
- `gc` 模块可手动控制;`__del__`、弱引用 `weakref`。

# §D Go 运行时(投 Go 岗必看)

## D1. GMP 调度模型(必考)
- **G**(goroutine 协程)、**M**(machine,OS 线程)、**P**(processor,逻辑处理器,持有可运行 G 队列,数量 = GOMAXPROCS)。
- M 必须绑定 P 才能执行 G;P 的本地队列 + 全局队列 + **work-stealing**(P 空了偷别的 P 的 G)。
- **goroutine 为什么轻**:初始栈仅 2KB(可增长)、用户态调度不陷内核、切换成本极低 → 轻松百万级。
- 遇到阻塞系统调用:M 与 P 解绑,P 去找/建别的 M 继续跑 G(不浪费)。

## D2. channel & CSP
- 理念:**"通过通信共享内存,而非通过共享内存通信"**。
- 无缓冲 channel(同步,收发都阻塞到配对)vs 有缓冲(满/空才阻塞)。
- `select` 多路复用 channel;易错:向已关闭 channel 发送 panic、nil channel 永久阻塞、goroutine 泄漏(没人收)。
- 也有 `sync.Mutex/RWMutex/WaitGroup/Once`,共享内存场景仍用锁。

## D3. GC:三色标记 + 写屏障
- **三色**:白(待回收)、灰(待扫描)、黑(已扫描存活)。从根开始把可达对象标黑。
- **并发 GC** + **写屏障**(标记期间业务在改引用,写屏障保证不漏标)→ STW 极短(亚毫秒)。
- **逃逸分析**:编译期判断对象是否"逃逸"出函数,不逃逸就分配在**栈**(随函数返回自动回收,不给 GC 添负担)。

> "我的 Agent 引擎是 **IO 密集**——大量时间在等 LLM 网关、向量库、DB。所以用 Python **asyncio** 单线程事件循环,`gather` 并行发起意图分类/实体抽取/记忆召回三路 IO,同步的 embedding 用 `to_thread` 丢线程池避免阻塞事件循环;GIL 在这种场景不是瓶颈。库存扣减这种**共享状态**的强一致操作,我不靠应用层锁,而是下沉到 **Redis 单线程原子命令(DECR)**,天然无锁防超卖。"
