## 案例 1 · IM 长连接接入架构(微信/QQ/钉钉)

**场景 & 难点**:消息要**实时、双向**触达,HTTP 请求-响应模式做不了服务端主动推 → 用**长连接**。海量设备同时在线,连接怎么管?

**架构要点**:
- **接入层(长连接网关)**:专门维持海量 TCP/WebSocket 长连接,与**业务逻辑层解耦**(接入层只管连接和收发,业务层无状态可水平扩)。
- **连接与用户映射**:`uid → 连接(哪台接入机的哪条连接)` 存路由表(Redis),发消息时按 uid 找到接入机再下推。
- **心跳保活**:客户端定期发心跳,服务端超时未收到就判定掉线、清理连接(应对 NAT 超时、假死连接)。
- **单机百万连接(C10M)**:靠 **epoll + Reactor + 少量线程**,连接态用内存少;Netty 是典型实现。

**⟵ 反查八股**:
- **长连接 vs 短连接 / TCP / 心跳**(见 [01 计网](01-network-os.md));为什么 HTTP 轮询不行(实时性差、无谓开销)。
- **IO 多路复用 epoll + Reactor**:单机海量连接的地基(见 [01 §8](01-network-os.md))。
- **无状态设计 + 水平扩展**:接入层有状态(连接),业务层无状态(见 [04 系统设计](04-distributed-mq-design.md))。
- **SSE / WebSocket / 长轮询** 对比(见 [01](01-network-os.md))。

**面试追问**:
- "10 万连接一台机怎么扛?" → epoll 事件驱动、非阻塞、连接内存开销小、业务下沉到无状态层。
- "用户在哪台接入机怎么知道?" → uid→接入机路由表(Redis),或一致性哈希。

**连接 ShopMesh**:我用 **SSE**(基于 HTTP 的服务端单向流)做流式回复,踩过"gzip/中间件缓冲把流缓成一次性返回"的坑(改纯 ASGI + 关 gzip 修好)——能讲清长连接/流式的工程细节。

## 案例 2 · IM 消息可靠投递:不丢 / 不重 / 不乱序(核心必考)

**场景 & 难点**:消息系统最重要的是"及时 + 准确"。准确 = **不丢、不重、不乱序**。**注意:TCP 的可靠只保证"到了对端协议栈",不保证"到了应用、落了库、用户看到了"** → 必须**应用层 ACK**。

**方案(三件套)**:
- **不丢:应用层 ACK + 重传**。发送方发消息 → 接收方**业务处理成功后回 ACK** → 发送方收到 ACK 才算送达,没收到就重传。(比 TCP ACK 更上层)
- **不重:msg_id 去重**。重传会导致重复 → 每条消息全局唯一 `msg_id`,接收端按 msg_id 幂等去重。
- **不乱序:seq 保序**。每个会话内单调递增 `seq`,接收端按 seq 排序、检测空洞(缺号则等待/拉取)。
- **多端同步**:一个人多设备,已读/收取状态要同步 → 每端维护自己的读游标。

**⟵ 反查八股**:
- **应用层 ACK vs 传输层可靠**:为什么 TCP 可靠还不够(见 [01 TCP](01-network-os.md))——经典陷阱题。
- **幂等 / 去重(唯一 msg_id)**:和 MQ 消费幂等、支付幂等**同一思想**(见 [04 §3](04-distributed-mq-design.md) + [05 案例 4](05-cases-ecommerce-seckill.md))。
- **有序性**:seq 单调递增 + 空洞检测(见 [03 有序性](03-concurrency-runtime.md))。
- **at-least-once + 幂等 ≈ exactly-once**:MQ 投递语义在 IM 的翻版(见 [04 MQ](04-distributed-mq-design.md))。

**面试追问**:
- "TCP 不是可靠吗,为什么还要应用 ACK?" → TCP 只保证字节到对端内核缓冲;应用崩溃/落库失败照样丢,业务视角必须应用层确认。
- "群消息 1 万人,ACK 会不会风暴?" → 群消息**读扩散**(见案例 3),ACK 优化/合并,大群特殊处理。

**连接 ShopMesh**:我的 webhook 幂等(支付回调按流水号去重)、Celery at-least-once 消费幂等,和 IM 的 msg_id 去重是**同一套"至少一次 + 幂等"**思想。

## 案例 3 · IM 离线消息 + 群聊(读扩散/写扩散 + 存储)

**场景 & 难点**:用户离线时的消息要存着、上线拉取;群聊 1 人发、N 人收,扩散怎么算?

**方案**:
- **离线消息**:用户不在线时消息存离线库(按 uid + seq);上线后**拉取离线消息 → 业务处理 → ACK → 服务端才删**(没 ACK 下次还拉,配 msg_id 去重防重复展示)。分页拉取避免一次拉太多客户端卡顿。
- **群聊扩散**:
  - **写扩散**:发群消息时写进每个成员的收件箱 → 读快,但大群写放大(和 Feed 推模式同理)。
  - **读扩散(大群常用)**:群消息只存一份(群信箱),成员**读时拉取** + 各自维护已读 seq → 写轻,适合万人大群。
- **消息存储**:海量消息 → 按会话/时间**分库分表**,冷热分离(近期热数据在快存储,历史归档)。

**⟵ 反查八股**:
- **写扩散 vs 读扩散**:和 [06 案例 1 Feed 推拉](06-cases-recsys-feed.md) **完全同构**(存储权衡)。
- **分库分表 + 冷热分离**(见 [02 §8](02-mysql-redis.md))。
- **游标/seq 分页拉取**(见 [06 案例 5](06-cases-recsys-feed.md))。

**面试追问**:"万人群为什么不写扩散?" → 1 条消息写 1 万次收件箱,写放大爆炸;读扩散只存一份、读时拉。

**连接 ShopMesh**:同 Feed——存储的推拉权衡我能从推荐 timeline 讲到 IM 群聊,是同一个"读多写少 vs 写多读少"的判断。

## 案例 4 · 微信红包(高并发资金交易,秒杀 + 金额分配的合体)

**场景 & 难点**:除夕数万群同时发抢红包;**发 100 元绝不能被拆出 101 元**(防超发/资损);没抢完 24h **精确退还**;抢红包是"数以万计并发抢锁",DB 压力远大于普通库存。

**方案要点**:
- **拆红包算法(二倍均值法)**:剩余金额 M、剩余人数 N,每次在 `[0, M/N×2]` 随机 → 期望公平、方差可控、和恒等于总额(**天然防超发**)。
- **预分配 vs 实时拆**:高并发下常**发红包时就把金额拆好存 Redis 队列**,抢的人**原子 pop 一份**(把"随机+扣减"变成"取一份"),避免并发算错。
- **防超发/一致性**:金额存 Redis 原子操作扣减;红包=一种"库存"(见 [05 案例 2](05-cases-ecommerce-seckill.md)),抢完即止。
- **削峰 + 异步入账**:抢到先返回"抢到 X 元",**异步**走账务落库(复式记账),削峰。
- **超时退款**:24h 未领完,定时任务精确退还剩余给发送方(**和你订单超时取消同构**)。
- **分库分表 + 单元化**:按红包 id/用户分片,分散热点。
- **降级**:极端流量下非核心链路降级,保抢红包主链路。

**⟵ 反查八股**:
- **防超发 = 秒杀防超卖**(Redis 原子/预分配,见 [05 案例 1/2](05-cases-ecommerce-seckill.md))。
- **金额精确 / 资损防护 / 复式记账 / 对账**(见 [05 案例 4 支付](05-cases-ecommerce-seckill.md))。
- **削峰 + 异步入账**(见 [04 MQ](04-distributed-mq-design.md))。
- **超时定时任务退款**(见 [05 案例 4] + 你项目超时取消)。
- **分库分表 / 单元化 / 降级**。

**面试追问**:
- "为什么预分配而不是抢的时候实时随机?" → 实时随机+扣减是复合操作,高并发下要加锁/Lua 才原子;预分配把它变成"原子取一份",更简单抗压。
- "金额怎么保证不多不少?" → 二倍均值和恒等于总额 + 原子扣 + 事后对账三重保证。

**连接 ShopMesh**:红包的"原子预扣 + 抢完即止 + 超时精确退还",和我的"库存原子预占 + 超时未支付释放"**是同一范式**,我能直接类比讲。

## 案例 5 · RPC 框架(Dubbo / gRPC)

**场景 & 难点**:微服务拆分后,服务间要像调本地方法一样调远程,还要解决"调哪台、序列化、失败重试"。

**核心流程(Dubbo)**:
1. **服务注册发现**:Provider 启动注册到**注册中心**;Consumer 订阅,注册中心**长连接推送**地址变更。
2. **动态代理**:Consumer 调本地接口,代理拦截 → 变成远程调用(对业务透明)。
3. **负载均衡**:从地址列表按算法(随机/轮询/最少活跃/一致性哈希)选一台。
4. **序列化**:参数编码(Dubbo 默认 Hessian2;gRPC 用 Protobuf)。
5. **网络传输**:**单一长连接 + NIO**(Netty),多路复用。
6. **集群容错**:Failover(失败重试别的机器,默认)/ Failfast(快速失败)/ Failsafe(失败忽略)/ Failback。

**⟵ 反查八股**:
- **RPC vs HTTP/REST**:RPC 长连接 + 二进制序列化,性能高、面向接口;HTTP 通用、跨语言、可读。
- **序列化**:Protobuf(跨语言、紧凑、快)vs JSON(可读、大);为什么二进制更快。
- **负载均衡算法**(见 [04 §7](04-distributed-mq-design.md))。
- **Netty / NIO / epoll / 长连接多路复用**(见 [01 §8](01-network-os.md))。
- **容错 / 重试 / 幂等**:重试要求接口幂等(见 [04](04-distributed-mq-design.md))。

**面试追问**:
- "RPC 为什么比 HTTP 快?" → 长连接复用免握手、二进制序列化更小更快、协议头精简。
- "失败重试要注意什么?" → 只对**幂等**接口重试(查询可重试,扣款不能盲重试)。

**连接 ShopMesh**:我项目 Java 控制面 ↔ Python 引擎经 RabbitMQ 异步事件通信(不是同步 RPC),但懂 RPC 与 MQ 的**同步/异步、耦合度**取舍;诚实说:这规模其实直连 HTTP 就够,双语言 + MQ 偏重了。

## 案例 6 · 注册中心 & 配置中心(ZK / Eureka / Nacos)

**场景 & 难点**:服务实例动态上下线,消费者要实时拿到"当前可用实例列表";配置要能**动态下发**(改配置不重启)。

**CP vs AP(高频对比)**:
| | 一致性 | 特点 |
|---|---|---|
| **ZooKeeper** | **CP** | 强一致;分区时为保一致可能**拒绝服务**(选主期间不可用) |
| **Eureka** | **AP** | 最终一致;分区时仍返回(可能过时的)实例列表,**保可用** |
| **Nacos** | **CP+AP 可切** | 既支持强一致(CP)也支持 AP;还兼**配置中心** |
- **面试爱问:注册中心该选 CP 还是 AP?** → 多数观点**倾向 AP**:注册中心分区时,宁可拿到一份"可能略旧"的实例列表(大概率仍可用),也不要因为追求强一致而整个注册中心不可用导致服务全崩。ZK 的 CP 在大规模注册/网络抖动场景反而有可用性风险。
- **健康检查**:心跳续约(超时未续 → 摘除实例);客户端还会本地缓存实例列表兜底。
- **配置中心(Nacos/Apollo)**:配置集中管理 + **变更实时推送**(长连接/长轮询)+ 灰度 + 版本回滚。

**⟵ 反查八股**:
- **CAP 落地**:注册中心是 CAP 权衡的经典实例(见 [04 §1](04-distributed-mq-design.md))。
- **ZK = ZAB / 强一致协调**(见 [04 一致性协议](04-distributed-mq-design.md))。
- **心跳 / 健康检查 / 客户端缓存兜底**(见案例 7 降级)。
- **长轮询 / 长连接推送配置**(见案例 1)。

**面试追问**:"ZK 做注册中心有什么问题?" → CP 特性:master 选举期间不可用;大量服务频繁上下线时,强一致写压力大、易雪崩 → 所以 Eureka/Nacos(AP)更受青睐。

**连接 ShopMesh**:我用 Traefik 做网关按路径分流,没上独立注册中心(服务少);但懂"服务发现 + 健康检查 + AP 优先"的原理,能说清什么规模才需要注册中心。

## 案例 7 · API 网关 + 支付渠道路由(网关类中间件)

**场景 & 难点**:①众多微服务不能直接暴露给客户端 → 统一入口。②支付要对接多渠道(微信/支付宝/银联),某渠道抖动要能切换。

**方案**:
- **API 网关(Nginx/Spring Cloud Gateway/Traefik)职责**:统一鉴权(校验 JWT)、**限流熔断**、路由转发、协议转换、灰度、日志监控、跨域。把横切关注点从各业务服务上收到网关。
- **支付渠道路由中间件(收银台)**:抽象统一支付接口,内部**路由**到具体渠道;按渠道**成功率/费率/健康度**选路,某渠道故障**自动降级切换**到备用渠道;对上层业务屏蔽渠道差异。

**⟵ 反查八股**:
- **网关 = 统一横切层**:限流/熔断/鉴权集中(见 [04 §6 限流熔断](04-distributed-mq-design.md))。
- **JWT 鉴权在网关做**(见 [01 §9](01-network-os.md))。
- **渠道降级/健康度路由 = 熔断降级思想**(见 [04 §6](04-distributed-mq-design.md))。
- **负载均衡 / 反向代理**(见 [04 §7](04-distributed-mq-design.md))。

**面试追问**:
- "鉴权为什么放网关不放各服务?" → 横切关注点上收,避免每个服务重复实现、便于统一策略。
- "网关会不会成为单点/瓶颈?" → 网关本身要集群 + 无状态 + 限流保护自己。

**连接 ShopMesh**:**这题我有真东西**——Traefik 网关按路径分流(`/api/auth`→Java、`/api/chat`→Python)、网关级限流、JWT 在入口校验(Java 签 RSA、Python 拉 JWKS 验签)。我能讲清网关横切 + 跨语言无状态鉴权,并诚实反思这套对当前规模偏重。
