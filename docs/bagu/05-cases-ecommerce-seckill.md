## 案例 1 · 秒杀系统全景(阿里双11 / 京东 / 秒杀中台)

**场景 & 难点**:某商品 1000 件,瞬时百万人抢。难点 = 瞬时**超高并发** + **绝不超卖** + **不能压垮 DB** + **防刷**。

**架构方案(分层拦截,层层过滤流量)**:
1. **前端**:按钮置灰、答题/验证码错峰、静态资源上 CDN。
2. **网关/Nginx**:限流 + 防刷(同一用户/IP 每秒 N 次),Nginx+Lua 直接拦。
3. **Redis 层**:`Lua 脚本`原子「校验+预扣库存+防重」,抢到资格才继续;**大部分流量在这里被挡住,根本不碰 DB**。
4. **MQ 削峰**:抢到资格的把下单请求丢 MQ(RocketMQ),**立即返回"排队中"**;后端消费者**匀速**落库下单。
5. **DB**:只承接被 Redis+MQ 削平后的涓涓细流。

**⟵ 反查八股**:
- **限流:令牌桶/漏桶/滑动窗口** → 网关挡住绝大多数流量(见 [04 §6](04-distributed-mq-design.md))。令牌桶允许突发,秒杀常用。
- **MQ 三大作用之"削峰"** → 洪峰入队、消费者匀速消费(见 [04 MQ](04-distributed-mq-design.md))。
- **Redis 单线程 + Lua 原子** → 预扣库存无锁防超卖(见 [02 Redis](02-mysql-redis.md))。
- **缓存 / CDN / HTTP 缓存** → 读静态化(见 [01 HTTP 缓存](01-network-os.md) + [02 缓存](02-mysql-redis.md))。
- **IO 多路复用/高并发** → Nginx/Redis 靠 epoll 抗海量连接(见 [01 §8](01-network-os.md))。
- **CAP/最终一致** → 抢到资格 ≠ 下单成功,异步落库,秒杀天然**最终一致 + 可用性优先**(AP 倾向)(见 [04 §1](04-distributed-mq-design.md))。

**面试追问**:
- "为什么不直接 DB 扣库存?" → 行锁热点、DB 扛不住百万 QPS;Redis 内存原子快几个量级。
- "MQ 挂了 / 消息丢了怎么办?" → 生产 confirm + Broker 持久化副本 + 消费手动 ACK;抢到资格但下单失败要**回补 Redis 库存**。
- "抢到资格没付款?" → 占用库存 → **超时未支付定时释放**(见案例 4)。

**连接 ShopMesh**:我的下单就是这套范式的最小版——**Redis 原子 DECR 预扣 + 超时未支付 Celery 对账释放**,只是没有百万级 QPS,所以没上 MQ 削峰;但知道流量再大一个量级该怎么加。

## 案例 2 · 库存扣减防超卖(交易系统核心)

**场景 & 难点**:高并发下 `查库存→判断>0→扣减` 三步非原子 → 并发交叉执行导致**超卖**。

**方案演进(经典成长线,面试爱问)**:
1. **DB 乐观锁**:`update stock set num=num-1 where id=? and num>0`(靠行锁 + 返回影响行数判断成功)。简单,但高并发下行锁热点、大量失败重试。
2. **DB 悲观锁**:`select ... for update` 锁行。串行化正确但吞吐差。
3. **Redis 原子预扣(主流)**:`DECR` 返回值 <0 就 `INCR` 回滚;或 **Lua 脚本**把「判断+扣减+防重」打包成一个原子操作。抗高并发,最终异步落库对账。
4. **分桶库存**:把 1000 件拆成 10 个 key 各 100,分散热点(进阶)。

**⟵ 反查八股**:
- **乐观锁(CAS/版本号)vs 悲观锁(for update)** → 读多写少用乐观、冲突多用悲观(见 [03 §A2](03-concurrency-runtime.md))。
- **Redis 单线程原子性 + Lua**:Lua 在 Redis 服务端整段原子执行,天然解决"检查-扣减"竞态(见 [02 Redis §7](02-mysql-redis.md))。
- **DB 行锁 / 索引**:乐观锁的 `where` 命中索引才是行锁,否则退化表锁(见 [02 §5](02-mysql-redis.md))。
- **幂等**:防同一用户重复扣(见案例 4)。

**面试追问**:
- "Redis 扣了、DB 落单失败怎么办?" → 补偿(回补 Redis)+ 对账兜底(见案例 3/4)。**这正是你 ShopMesh 的补偿式一致故事。**
- "为什么 Lua 不用事务 MULTI?" → Redis 事务不支持中途逻辑判断/回滚,Lua 能带判断且整段原子。

**连接 ShopMesh**:我用 `DECRBY` + 失败 `INCRBY` 回滚做原子预占,多 item 任一失败回滚已占——就是这条线的第 3 级。

## 案例 3 · 订单-库存 跨服务分布式事务(RocketMQ 事务消息)

**场景 & 难点**:下单要"创建订单(订单库)+ 扣库存(库存库)+ 清购物车 + 加积分",跨多服务/多库,**不能用单机事务**,又不能订单成功而库存没扣。

**方案:RocketMQ 事务消息(可靠消息最终一致)**:
1. 生产者发**半消息(half message)**到 MQ(消费者暂不可见)。
2. MQ 回调执行**本地事务**(创建订单 + 写本地事务状态表)。
3. 本地事务成功 → **commit** 半消息(消费者可见);失败 → rollback(丢弃)。
4. 若 MQ 长时间没收到二次确认 → **回查**本地事务状态表定状态。
5. 下游(库存服务)消费消息扣库存,失败重试;**消费幂等**防重复扣。

对比:也可用**本地消息表**(业务表 + 消息表同库事务落地,再异步投递),思想一致、不依赖 MQ 事务特性。

**⟵ 反查八股**:
- **分布式事务:事务消息 / 本地消息表 / Saga / TCC / 2PC** 全谱系(见 [04 §3](04-distributed-mq-design.md))——这案例是"事务消息"的标准落地。
- **MQ 投递语义 at-least-once → 消费者幂等**(见 [04 MQ §2](04-distributed-mq-design.md))。
- **最终一致 / BASE**(见 [04 §2](04-distributed-mq-design.md))。
- **两阶段思想**:事务消息的 half+commit 与 DB 的 redo/binlog 2PC 神似(见 [02 §6](02-mysql-redis.md))。

**面试追问**:
- "为什么不用 2PC?" → 2PC 同步阻塞、协调者单点、慢,互联网偏好异步最终一致。
- "消息回查是干嘛的?" → 兜住"本地事务执行完但 commit 消息丢了"的中间态。
- "消费失败一直重试怎么办?" → 重试上限 → 进**死信队列**人工/补偿处理。

**连接 ShopMesh**:我没上 RocketMQ 事务消息(规模不需要),用的是更轻的**补偿 + 对账**;但能说清"规模上来后,订单-库存解耦我会用事务消息或本地消息表做最终一致"。

## 案例 4 · 支付系统(幂等 · 回调 · 对账 · 资损防护)

**场景 & 难点**:钱的事,**绝不能多扣/少扣/重复扣**;第三方支付**异步回调**可能重复/丢失/乱序;网络超时下"到底付没付"要能查证。

**方案要点**:
- **幂等**:支付请求带 `幂等键`(唯一索引);回调用支付流水号去重,重复回调直接返回。
- **只信回调 + 验签**:订单转"已支付"只由支付方**服务端异步回调**触发,且**验签**(HMAC/RSA)防伪造;前端"支付成功"页不可信。
- **状态机**:待支付→已支付→…,转移有前置校验,非法转移拒绝。
- **回调不可靠 → 主动查询 + 定时重试**:回调可能丢,支付系统还会**主动查支付方**对状态;通知下游失败进**延迟重试框架**。
- **对账(最后防线)**:每日与支付方账单逐笔核对,发现差异(己方无/对方无/金额不符)→ 调账,**防资损**。

**⟵ 反查八股**:
- **幂等设计**(唯一键 / 去重表 / 状态机)(见 [04 §3](04-distributed-mq-design.md) + 案例 3)。
- **HMAC / webhook 安全 / 常量时间比较**(见 [00 清单] + 你项目)。
- **最终一致 + 对账兜底**:分布式对钱的终极保障。
- **MQ 重试 / 延迟队列 / 死信**:通知下游(见 [04 MQ](04-distributed-mq-design.md))。
- **状态机**:订单/支付状态流转(见案例 6 履约同理)。

**面试追问**:
- "回调和主动查询都来了,状态会乱吗?" → 幂等 + 状态机前置校验,谁先到都只推进一次。
- "为什么对账是最后防线?" → 前面所有机制都可能有 bug/网络黑洞,对账用"事后逐笔核对"兜底,资损可发现可追。

**连接 ShopMesh**:**这题几乎是我项目的原话**——支付只信 HMAC 验签 webhook(伪造回调实测被拒)、幂等键、状态机、超时对账取消。面试到这题我能直接掏代码级细节。

## 案例 5 · 分布式订单号 / ID(美团 Leaf)

**场景 & 难点**:分库分表后不能用 DB 自增;订单号要**全局唯一 + 趋势递增(利于 B+ 树索引)+ 高性能 + 高可用**,还常要求"不暴露业务量"(别人不能靠 ID 猜你日单量)。

**方案(美团 Leaf 两种模式)**:
- **Leaf-segment 号段模式**:从 DB 批量取一段 ID(如一次 1000 个)缓存在内存发,**双 buffer** 预取下一段(当前段用到 10% 就异步取下一段)→ 即使 DB 短时宕机仍能发号 10~20 分钟。TP999 ~1ms,QPS 近 5w。
- **Leaf-snowflake 雪花模式**:64 位 = 1 符号 + 41 时间戳(ms)+ 10 workId + 12 序列;**workId 用 ZooKeeper 顺序节点**自动分配,解决"手动配机器 ID"运维痛点;处理**时钟回拨**。

**⟵ 反查八股**:
- **分布式 ID 方案对比(UUID/雪花/号段/Redis)**(见 [04 §4](04-distributed-mq-design.md))。
- **雪花位分配 + 时钟回拨**(见 [04 §4](04-distributed-mq-design.md))。
- **趋势递增为什么重要** → 随机 ID(UUID)做主键会导致 B+ 树**页分裂**、写放大(见 [02 §1 聚簇索引/自增主键](02-mysql-redis.md))。
- **ZooKeeper 顺序节点**(见 [04 分布式锁/协调](04-distributed-mq-design.md))。
- **双 buffer 预取** = 用空间换"DB 抖动不影响发号"的可用性(异步预加载思想)。

**面试追问**:
- "为什么不直接 UUID?" → 无序、128 位太长、做主键页分裂。
- "号段模式 DB 挂了还能发号吗?" → 能,内存里还有一整段 + 预取的下一段。
- "雪花时钟回拨怎么办?" → 拒绝发号并等待 / 用扩展位 / 切备用时钟。

**连接 ShopMesh**:我订单号用 `ORD-{uuid hex}`——够用但不趋势递增。面试可主动说:"规模上来我会换雪花/号段,理由是 UUID 做主键的页分裂问题。"(反思式加分)

## 案例 6 · 商品详情页高并发读(多级缓存 + 热点 key)

**场景 & 难点**:爆款详情页 QPS 数万~数十万,**读多写极少**;热点 key 统一过期瞬间会**缓存击穿**打垮 DB。

**方案:三级缓存 + 热点治理**:
1. **CDN / 页面静态化**:详情页大部分是静态的,直接 CDN 命中。
2. **Nginx 本地缓存**(Lua)→ **Redis 分布式缓存** → **应用堆内本地缓存(Caffeine)**,逐级兜底,越靠前越抗量。
3. **热点 key**:探测出爆款 → **"永不过期 + 分布式锁单线程重建 + 后台异步兜底更新"**,杜绝击穿;本地缓存 + 热点探测(如有赞 TMC)减少对 Redis 的冲击。
4. **一致性**:详情页库存**可短暂不一致**(展示用),**下单时再校验真实库存**——用短 TTL 容忍。

**⟵ 反查八股**:
- **多级缓存架构 + 本地缓存 vs 分布式缓存**(见 [02 Redis](02-mysql-redis.md))。
- **缓存三兄弟:穿透/击穿/雪崩**——热点 key 治理正是防击穿(见 [02 §5](02-mysql-redis.md))。
- **缓存与 DB 一致性:最终一致 + TTL 兜底**(见 [02 §6](02-mysql-redis.md))——"展示可不一致、下单必一致"是经典权衡。
- **HTTP 缓存 / CDN**(见 [01 §8](01-network-os.md))。
- **读写分离**(见 [02 §8](02-mysql-redis.md))。

**面试追问**:
- "本地缓存和 Redis 不一致怎么办?" → 本地缓存设短 TTL + 变更时广播失效(MQ/发布订阅);容忍秒级不一致。
- "热点 key 怎么发现?" → 实时统计访问频次(滑动窗口计数),超阈值标热点走特殊策略。

**连接 ShopMesh**:我的门店/商品是 Qdrant + JSON,读路径没做多级缓存(规模不需要);但"展示可不一致、下单必一致"这条我在秒送里就是这么设计的(门店卡片展示的 ETA 是估算,下单再确认)。

## 案例 7 · 购物车系统

**场景 & 难点**:高频读写、要跨端同步、未登录也能加购、登录后要合并。

**方案**:
- **存储**:登录用户购物车用 **Redis Hash**(`cart:{uid}` → field=商品id、value=数量/快照),读写快、天然按用户隔离;定期/异步落库持久化。未登录存**浏览器本地(Cookie/localStorage)**,登录后**合并**到服务端。
- **价格快照仅展示**:下单时**服务端按实时价重算**,不信购物车快照(防改价)。

**⟵ 反查八股**:
- **Redis 数据结构选型(Hash)+ 持久化**(见 [02 Redis §1/§3](02-mysql-redis.md))。
- **Session vs Token / 登录态**:未登录→登录的身份合并(见 [01 §9](01-network-os.md))。
- **缓存与 DB 一致**:购物车异步落库(见 [02 §6](02-mysql-redis.md))。

**面试追问**:"为什么用 Hash 不用 String 存整个购物车 JSON?" → Hash 能单独改一个商品的数量(field 级),不用读写整个对象;并发更友好。

**连接 ShopMesh**:**又是原话**——我购物车就是 `cart:{user_id}` 的 Redis Hash,field=product_id,下单时服务端重算价不信快照。

## 案例 8 · 优惠券发放 / 领取(秒杀同构)

**场景 & 难点**:限量券"先到先得",本质就是**秒杀**(防超发);还要防**同一用户重复领**;发行量大要**分库分表**。

**方案**:
- **防超发**:发行量放 Redis,领取走 **Lua 原子预扣**(同案例 2)。
- **防重复领**:`用户id+活动id` 唯一键(Redis Set 或 DB 唯一索引)幂等。
- **异步落库 + MQ**:抢到后异步写"用户券"表,削峰。
- **分库分表**:用户券表按 `user_id` 哈希分片(保证一个用户的券在同库,便于查)。

**⟵ 反查八股**:
- **秒杀全套**(限流/Redis 原子/MQ 削峰,见案例 1/2)。
- **幂等(唯一键)**(见 [04 §3](04-distributed-mq-design.md))。
- **分库分表:分片键选择**(按 user_id 保证查询不跨库)(见 [02 §8](02-mysql-redis.md))。

**面试追问**:"券表为什么按 user_id 分而不是券 id?" → 高频查询是"我的券列表",按 user_id 分片能单库查完,不用聚合多库。
