# 第一部分:分布式理论

## 1. CAP(必考)
- **C 一致性**:所有节点同一时刻数据一致。**A 可用性**:请求都有(非错)响应。**P 分区容错**:网络分区时系统仍工作。
- **只能三选二,且 P 必选**(分布式网络分区不可避免)→ 实际是 **CP vs AP** 权衡。
  - **CP**:分区时为保一致性拒绝服务(ZooKeeper、etcd、HBase)。
  - **AP**:分区时保可用返回可能旧的数据(Eureka、Cassandra、多数缓存)。
- 一句话:**网络正常时 CA 都能要;分区发生时,在 C 和 A 之间选。**

## 2. BASE(对 CAP 中 AP 的实践延伸)
- **B**asically **A**vailable(基本可用,可降级)+ **S**oft state(软状态,允许中间态)+ **E**ventually consistent(**最终一致**)。互联网大多数系统的实践哲学:不追强一致,追最终一致 + 高可用。

## 3. 分布式事务(必考,你项目相关)
| 方案 | 思想 | 优/缺 | 场景 |
|---|---|---|---|
| **2PC**(两阶段提交) | 协调者:prepare→commit | 强一致;**同步阻塞、协调者单点、慢** | DB/XA |
| **3PC** | 加超时 + CanCommit | 减阻塞;更复杂,仍非完美 | 少用 |
| **TCC** | Try(预留)→ Confirm/Cancel | 灵活、性能好;**业务侵入大**(写三个接口) | 资金、订单 |
| **本地消息表** | 业务与"待发消息"同库事务落地,再异步投递 | 简单可靠、最终一致;有延迟 | 通用 |
| **事务消息**(RocketMQ) | 半消息 → 本地事务 → 提交/回滚消息 | 解耦、可靠;依赖 MQ | 电商解耦 |
| **Saga** | 一串本地事务 + 每步的**补偿操作** | 长事务、无锁;**无隔离性**,要幂等 | 跨服务长流程 |
| 最大努力通知 | 定时重试通知,不保证 | 弱 | 对账、回调 |
- **你项目的落地**:下单是 Redis 扣库存 + PG 落单跨存储 → 用**补偿式(Saga-lite)**:失败释放库存 + **对账任务**兜底(超时未支付自动取消释放)。**会讲这个 = 把简历坑变亮点。**

## 4. 分布式 ID(必考)
- 要求:全局唯一、趋势递增(利于 DB 索引)、高性能、高可用。
- 方案:
  - **UUID**:唯一但无序、太长、不适合做主键(页分裂)。
  - **雪花算法 Snowflake**:64 位 = 1 符号 + 41 时间戳(毫秒)+ 10 机器 ID + 12 序列号。**趋势递增、高性能、本地生成**。坑:**时钟回拨**(要处理:等待/拒绝/用备用位)。
  - **号段模式**(美团 Leaf):DB 批量取一段 ID 到内存发,减少 DB 访问。
  - **Redis INCR**:原子自增,依赖 Redis 可用性。

## 5. 一致性协议(会讲即可,常考 Raft)
- **Raft**(易懂,etcd/Consul 用):
  - **角色**:Leader / Follower / Candidate。
  - **选主**:Follower 超时没收到心跳 → 变 Candidate 发起投票 → **过半**票当选 Leader;任期 term 防脑裂。
  - **日志复制**:客户端写只走 Leader → Leader 追加日志并复制给 Follower → **过半确认**才 commit 并应答 → Follower 应用。
  - 保证:同一 term 只有一个 Leader;已提交日志不丢。
- **Paxos**:更早、更难懂,Raft 是其工程化简化。**ZAB**:ZooKeeper 用,类似。
- **一致性哈希**:节点/数据映射到环上,顺时针找节点;加/删节点只影响相邻区间(而非取模全量迁移);**虚拟节点**解决数据倾斜。用于分布式缓存/分片。

## 6. 高可用三板斧:限流 / 熔断 / 降级(必考)
- **限流算法**:
  - 计数器(固定窗口,有临界突刺问题)
  - **滑动窗口**(平滑临界)
  - **漏桶**(恒定速率流出,削峰但不允许突发)
  - **令牌桶**(匀速发令牌,**允许一定突发**,最常用)
- **熔断**:依赖故障时快速失败,不再打它。**熔断器三态**:Closed(正常)→ 失败率超阈值 → Open(直接拒绝)→ 半开 Half-Open(放少量试探)→ 恢复则 Closed。(Hystrix/Sentinel/Resilience4j)
- **降级**:非核心功能关闭/返回兜底(如推荐挂了返回热门榜)。**隔离**:线程池/信号量隔离,防一个依赖拖垮全部(舱壁模式)。

## 7. 负载均衡
- 算法:轮询、加权轮询、随机、**最少连接**、一致性哈希(会话粘连)、IP hash。
- 层级:DNS(地域)、四层 LVS(IP+端口)、七层 Nginx/网关(按 URL/header)。

# 第二部分:消息队列(MQ)

## 1. 作用(三大)
- **解耦**:生产者不关心谁消费。
- **异步**:非核心流程异步做(下单后发短信/加积分),缩短主链路 RT。
- **削峰**:流量洪峰先入队,消费者匀速处理(秒杀)。
- 代价:系统复杂度、一致性、消息可靠性问题。

## 2. 四大经典问题(必考)
- **消息丢失**(三段保证):
  - 生产端:发送确认(ack / confirm),失败重试。
  - Broker 端:**持久化 + 副本**(刷盘 + 多副本)。
  - 消费端:**手动 ACK**(处理成功再确认,别自动 ACK)。
- **消息重复**(MQ 基本是 **at-least-once**,重复难免)→ **消费者幂等**(唯一业务 ID + 去重表 / 状态机 / DB 唯一键)。
- **消息顺序**:全局有序难(单分区+单消费,吞吐低);一般**局部有序**——同一业务 key 路由到**同一分区/队列**,单线程消费。
- **消息积压**:消费太慢 → 加消费者(≤ 分区数)、批量消费、排查慢点;紧急时先扩分区/临时转存。

## 3. 投递语义
- **at-most-once**(最多一次,可能丢)、**at-least-once**(最少一次,可能重,最常用)、**exactly-once**(恰好一次,难,靠"at-least-once + 幂等/事务"近似实现)。

## 4. 三大 MQ 对比(知道选型即可)
| | Kafka | RabbitMQ | RocketMQ |
|---|---|---|---|
| 定位 | 高吞吐、日志/大数据流 | 灵活路由、低延迟、业务 | 电商、事务消息、金融 |
| 吞吐 | 极高(百万级) | 万级 | 十万级 |
| 特色 | 分区、pull、生态强 | Exchange 路由灵活 | **事务消息**、顺序、延迟 |
- **Kafka 为什么高吞吐**:**顺序写磁盘**(比随机写快)、**页缓存(pagecache)**、**零拷贝 sendfile**、**分区并行**、批量 + 压缩。

# 第三部分:系统设计方法论

## 1. 通用套路(白板题按这个走)
1. **需求澄清**:功能(要做什么)+ 非功能(QPS、数据量、读写比、延迟、一致性要求)。
2. **容量估算**:日活/QPS(峰值 ≈ 平均×(2~10))、存储(条数×单条大小×天数)、带宽。
3. **接口设计**:核心 API(REST)。
4. **数据模型**:表/字段/索引;选 SQL 还是 NoSQL。
5. **整体架构**:客户端→网关/LB→服务→缓存/DB/MQ,分层画出。
6. **扩展与优化**:读多→**缓存 + 读写分离**;写多/数据大→**分库分表 + 异步**;高并发→**MQ 削峰 + 限流降级**;热点→本地缓存/多级缓存。
7. **权衡与兜底**:一致性 vs 可用性、单点、容灾、监控。

## 2. 高频设计题速记
- **短链系统**:发号器(雪花/号段)→ 62 进制编码短码;`短码→长链` 存 KV(Redis + DB);302 重定向;防重(长链 hash 去重)。QPS 读远大于写 → 重缓存。
- **秒杀**:①**读多**:静态化 + CDN + 缓存 ②**防超卖**:Redis 预扣库存(原子 DECR/Lua)③**削峰**:MQ 异步下单 ④**限流 + 防刷**(用户/IP 限流、验证码、隐藏 URL)⑤最终一致对账。**←你项目的交易设计能直接对话这题。**
- **Feed 流**:推模式(写扩散,发帖写进所有粉丝收件箱,读快写重,适合普通用户)vs 拉模式(读扩散,读时聚合关注的人,写快读重,适合大 V)→ **推拉结合**。
- **分布式限流**:Redis + Lua 实现令牌桶/滑动窗口(原子)。
- **点赞/计数**:Redis 计数 + 异步落库;防重用 Set/Bitmap。

## 3. 一句话价值观(面试官爱听)
> "**没有银弹,都是权衡**":加缓存换一致性、分库分表换复杂度、异步换实时性。设计时先问清**读写比、数据量、一致性要求**,再对症下药——不要过度设计(我自己项目就踩过双语言/MQ 过度设计的坑,现在会先简单再演进)。

## 与你项目的连接点(面试可主动举例)
- **分布式事务** → 下单跨 Redis+PG 的补偿式一致 + 对账兜底。
- **幂等** → idempotency_key 唯一索引防重复下单。
- **限流/降级** → 网关限流 + LLM 不可用时降级到确定性检索。
- **MQ** → Celery+RabbitMQ 承载异步记忆写入/事件;at-least-once → 任务幂等。
- **缓存** → Redis 会话窗口/库存/购物车;缓存与 DB 最终一致。
- **秒杀设计** → 你的"原子预扣 + 幂等 + 超时释放"就是秒杀防超卖的标准范式。
