# 第一部分:MySQL(InnoDB)

## 1. 索引 & B+ 树(必考核心)
**为什么用 B+ 树,不用二叉树/红黑树/B 树/哈希?**
- 二叉/红黑树:树太高 → 磁盘 IO 次数多(每层一次 IO)。
- **B+ 树**:多叉、矮胖(3~4 层存千万级)、**只有叶子存数据**、**叶子用双向链表连**。→ 磁盘 IO 少、**范围查询/排序快**(顺着叶子链走)。
- B 树 vs B+ 树:B 树非叶也存数据 → 单节点能放的 key 少、树更高;范围查要中序遍历。
- **哈希索引**:等值 O(1) 但**不支持范围/排序**,且哈希冲突。

**关键概念:**
- **聚簇索引(主键索引)**:叶子存**整行数据**。InnoDB 表数据就是按主键组织的 B+ 树。→ 建议用**自增主键**(避免页分裂)。
- **二级索引(普通索引)**:叶子存**主键值**;查非主键列 → 先查二级索引拿主键 → 再回主键索引查整行 = **回表**。
- **覆盖索引**:查询列都在索引里 → 不用回表(`explain` 见 `Using index`)。
- **最左前缀原则**:联合索引 `(a,b,c)` 能用于 `a`、`a,b`、`a,b,c`,不能跳 `a` 直接用 `b`。范围查询(`>` `<` `like 前缀`)后面的列用不上索引。
- **索引失效场景(高频)**:①对索引列用函数/运算 ②隐式类型转换(字符串列传数字)③`like '%x'` 前导通配 ④`or` 连接非索引列 ⑤违反最左前缀 ⑥优化器认为全表扫更快。

## 2. 事务 ACID
- **A 原子性**:全部成功或全部回滚 → **undo log**。
- **C 一致性**:约束不被破坏(目的,靠其它三个 + 业务保证)。
- **I 隔离性**:并发事务互不干扰 → **锁 + MVCC**。
- **D 持久性**:提交后不丢 → **redo log**。

## 3. 隔离级别 & 并发问题(必考)
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 RU | ✔ | ✔ | ✔ |
| 读已提交 RC | ✗ | ✔ | ✔ |
| **可重复读 RR**(MySQL 默认) | ✗ | ✗ | ✔(InnoDB 用间隙锁基本解决) |
| 串行化 | ✗ | ✗ | ✗ |
- **脏读**:读到别的事务未提交的数据。
- **不可重复读**:同一事务两次读同一行结果不同(别人改了并提交)。
- **幻读**:同一事务两次范围查,行数变了(别人插了新行)。

## 4. MVCC(多版本并发控制,重点)
- 目的:**读不加锁**、读写不阻塞,提升并发。
- **实现三件套**:
  - **隐藏列**:`DB_TRX_ID`(最近改它的事务)、`DB_ROLL_PTR`(指向 undo log 里的旧版本)。
  - **undo log 版本链**:每次改都把旧值串成链。
  - **Read View(一致性视图)**:记录生成快照那刻「活跃(未提交)事务列表」。判断某版本是否可见:该版本的 trx_id 若已提交(不在活跃列表、且 ≤ 最小活跃 id 或 < 创建时的最大 id)则可见,否则顺 roll_ptr 找更旧版本。
- **RC vs RR 区别就在 Read View 生成时机**:RC **每次 select** 都生成新 view(所以能读到别人新提交的 → 不可重复读);RR **事务第一次 select** 生成一次、之后复用(所以可重复读)。
- **快照读 vs 当前读**:普通 `select` = 快照读(走 MVCC);`select ... for update`、`update/delete` = 当前读(读最新 + 加锁)。
- **RR 怎么防幻读**:快照读靠 MVCC;当前读靠**间隙锁/临键锁**锁住区间防插入。

## 5. 锁
- 粒度:全局锁、表锁、**行锁**(InnoDB,基于索引;**无索引会退化成表锁**)。
- 类型:共享锁 S(读)、排他锁 X(写);意向锁 IS/IX(表级,表示表内有行锁,加表锁时快速判断)。
- 行锁三种:**记录锁**(锁某行)、**间隙锁 Gap**(锁区间,防插入)、**临键锁 Next-Key**(记录锁+间隙锁,RR 默认,防幻读)。
- 死锁:两事务互相等对方的锁;InnoDB 会检测并回滚代价小的一方。避免:**固定加锁顺序**、缩小事务、降低隔离级别。

## 6. 日志(必考)redo / undo / binlog + 两阶段提交
- **redo log**(InnoDB,物理日志,循环写):记录「对某页做了什么改」。**WAL(Write-Ahead Log)** 先写日志再刷盘 → **crash-safe**(崩溃后重放未落盘的改)。
- **undo log**(逻辑日志):记录反向操作,用于**回滚** + **MVCC 版本链**。
- **binlog**(Server 层,逻辑日志,追加写):记录 SQL 逻辑变更,用于**主从复制、数据恢复**。
- **两阶段提交(2PC,保证 redo 与 binlog 一致)**:
  1. 写 redo log,置 **prepare**
  2. 写 binlog
  3. 提交事务,redo 置 **commit**
  - 崩溃恢复:redo 有 commit → 提交;redo 只有 prepare 但 binlog 完整 → 提交;否则回滚。防止「主库改了但 binlog 没记 → 从库丢数据」或反之。

## 7. 一条 SQL 的执行流程
连接器(鉴权)→ 查询缓存(8.0 删了)→ 分析器(词法/语法)→ 优化器(选索引、join 顺序)→ 执行器(调存储引擎)→ InnoDB(操作 + 写 redo/undo/binlog)。

## 8. 主从复制 & 分库分表
- **主从复制**:主写 binlog → 从库 IO 线程拉取写 relay log → 从库 SQL 线程重放。**读写分离**分摊读压力。有**主从延迟**(可读主/半同步/并行复制缓解)。
- **分库分表**:垂直拆(按业务/字段)、水平拆(按 range / **hash 取模** / 一致性哈希)。带来:分布式 ID、跨库 join/事务、扩容迁移难题 → 中间件 ShardingSphere / MyCat。
- 何时分:单表**千万级**、单库连接/容量瓶颈时;能加缓存/优化索引先别急着分。

## 9. 优化套路
`explain` 看 type(全表 ALL 差、ref/range 好、const 最好)、key(用了哪个索引)、rows、Extra(Using index 覆盖 / Using filesort 排序 / Using temporary)。慢查询:加合适索引、覆盖索引、避免 select *、避免大 offset 分页(用游标/延迟关联)。

# 第二部分:Redis

## 1. 五大数据结构 + 底层(必考)
| 类型 | 底层(编码) | 场景 |
|---|---|---|
| String | int / **SDS**(简单动态字符串) | 缓存、计数、分布式锁、Session |
| List | quicklist(ziplist+双向链表) | 消息队列、时间线 |
| Hash | listpack/ziplist / hashtable | 对象属性 |
| Set | intset / hashtable | 去重、标签、共同好友(交并差) |
| ZSet | listpack / **skiplist + hashtable** | 排行榜、延迟队列、范围查 |
- 补充:Bitmap(签到)、HyperLogLog(基数估算 UV)、GEO(附近的人)、Stream(消息队列)。
- **SDS 为什么不用 C 字符串**:O(1) 取长度、二进制安全、防缓冲区溢出、预分配减少 realloc。
- **skiplist(跳表)为什么用它不用红黑树**:实现简单、范围查询天然(ZSet 要范围)、并发/调整成本低。

## 2. Redis 为什么快
①纯**内存** ②**单线程**避免锁竞争与上下文切换 ③**IO 多路复用(epoll)**处理海量连接 ④高效数据结构。
- **6.0 引入多线程**:只用于**网络 IO 读写/协议解析**(瓶颈在网络),**命令执行仍单线程**(保持无锁简单)。

## 3. 持久化:RDB vs AOF
- **RDB**:某时刻**内存快照**(二进制,紧凑)。优:恢复快、文件小、适合备份。缺:会丢最后一次快照后的数据;fork 子进程有开销。
- **AOF**:记录**每条写命令**(追加)。`appendfsync`:always(不丢但慢)/ **everysec(默认,最多丢 1s)** / no。优:丢数据少。缺:文件大、恢复慢 → **AOF 重写(rewrite)** 压缩。
- **混合持久化(4.0+)**:AOF 重写时前半段 RDB 二进制 + 后半段增量 AOF → 兼顾恢复快与丢数据少。

## 4. 过期删除 + 内存淘汰
- **过期键删除**:①**惰性删除**(访问时才查过期,省 CPU 但可能留垃圾)②**定期删除**(周期随机抽查一批)。两者结合。
- **内存淘汰(maxmemory 满时)8 策略**:noeviction(默认,拒写)、**allkeys-lru / allkeys-lfu / allkeys-random**、volatile-lru / volatile-lfu / volatile-random / volatile-ttl(带 volatile 的只淘汰设了过期的)。**LFU(4.0+)** 按访问频率,比 LRU 更抗偶发大 key。

## 5. 缓存三兄弟(必考)
- **缓存穿透**:查**不存在**的数据,每次都打到 DB。解:①**布隆过滤器**(判断一定不存在就拦)②缓存**空值**(短 TTL)③接口校验。
- **缓存击穿**:某**热点 key 过期**瞬间,大量请求同时打 DB。解:①**互斥锁/单飞**(只放一个去重建)②热点 key **逻辑过期**(不真过期,后台异步重建)。
- **缓存雪崩**:**大量 key 同时过期** 或 Redis 宕机,请求全打 DB。解:①过期时间**加随机抖动** ②多级缓存 ③Redis 高可用(哨兵/集群)④限流降级。

## 6. 缓存与 DB 一致性(高频)
- **旁路缓存 Cache Aside(最常用)**:读:先读缓存,miss 则读 DB 并回填。写:**更新 DB + 删除缓存**(不是更新缓存)。
- **为什么删不是更新**:更新缓存有并发覆盖旧值风险 + 可能算了没人读的值;删缓存让下次读时回填最新。
- **为什么先更 DB 再删缓存**:先删缓存再更 DB,中间有请求会把旧值又读进缓存 → 不一致。先更 DB 再删,窗口更小。
- **残留不一致(读旧值刚好在删之前回填)**:用**延迟双删**(更 DB 后删一次,延迟再删一次)或给缓存**设 TTL 兜底** + 订阅 binlog(canal)异步删。
- 结论:缓存一致性只能做到**最终一致**,想强一致就别用缓存(或加分布式锁,代价大)。

## 7. 分布式锁(必考,你项目用到)
- **核心命令**:`SET key value NX EX 30`(NX 不存在才设=互斥,EX 过期=防死锁)。
- **value 要唯一(如 UUID)**:释放时**先比对 value 再删**,防止「A 的锁超时被 B 拿到,A 又来把 B 的删了」。
- **比对+删要原子** → 用 **Lua 脚本**(GET 比对 == 就 DEL)。
- **锁过期但业务没完** → **看门狗(watchdog)** 自动续期(Redisson 实现)。
- **Redlock**:多个独立 Redis 节点过半加锁成功才算;有争议(Martin Kleppmann 质疑其在时钟漂移/GC 停顿下的安全性)。面试知道存在 + 争议即可。
- **vs ZooKeeper 锁**:ZK 临时顺序节点 + watch,天然处理宕机(session 断锁自动释放),一致性强但性能低于 Redis。

## 8. 高可用
- **主从**:读写分离 + 数据备份,但主挂需人工切。
- **哨兵 Sentinel**:监控主从,主挂自动**故障转移**(选新主),客户端从哨兵拿地址。解决高可用,不解决容量。
- **Cluster 集群**:**16384 个 slot** 按 CRC16 分片到多主,横向扩容 + 高可用(每主带从)。不支持跨 slot 多 key 事务(需 hash tag)。
