## 案例 1 · Feed 流:推模式 / 拉模式 / 推拉结合(微博、朋友圈,10 亿级)

**场景 & 难点**:用户关注一堆人,首页时间线要按时间/热度聚合关注对象的新内容。难点 = **读写放大失衡** + 大 V 千万粉丝。

**三种模式(必考)**:
- **推模式(写扩散)**:发帖时**主动写进所有粉丝的收件箱(timeline)**。→ 读快(直接读自己收件箱),但**写放大巨大**(大 V 一发,千万次写)。适合粉丝少的普通用户。
- **拉模式(读扩散)**:发帖只写自己;用户**读时实时拉取所有关注人的内容再聚合排序**。→ 写轻,但**读慢**(关注 2000 人就要聚合 2000 路)。
- **推拉结合(10 亿级标配)**:**普通用户用推**(写扩散到粉丝),**大 V 用拉**(粉丝读时才实时拉大 V 内容)。发帖时先判断"我是不是大 V",分流处理。既避免大 V 写爆,又保证普通内容读得快。

**⟵ 反查八股**:
- **存储权衡:写扩散 vs 读扩散** = 典型"读多写少 → 预计算换读性能;写多 → 读时聚合"的权衡(见 [04 系统设计方法论](04-distributed-mq-design.md))。
- **Redis** 存 timeline(List/ZSet 按时间/分数),收件箱模型。
- **缓存 + 热点**:大 V 内容是超级热点 key,配合多级缓存(见 [05 案例 6](05-cases-ecommerce-seckill.md))。
- **MQ 削峰**:发帖写扩散异步化(丢 MQ 慢慢扩散),避免同步写爆(见 [04 MQ](04-distributed-mq-design.md))。
- **分库分表**:timeline 按 user_id 分片(见 [02 §8](02-mysql-redis.md))。

**面试追问**:
- "大 V 发帖为什么不能纯推?" → 千万粉丝 = 千万次写,瞬间打爆;且很多僵尸粉根本不看,白扩散。
- "推拉结合的边界(谁算大 V)怎么定?" → 粉丝数阈值 + 活跃度动态调整。
- "翻页不重不漏怎么保证?" → 见案例 5。

**连接 ShopMesh**:我的场景是"每次对话即时检索",不是关注型 timeline,所以没做推拉;但能讲清"如果做导购的关注/订阅 feed,普通商家推、头部商家拉"。

## 案例 2 · 推荐级联架构:召回 → 粗排 → 精排 → 重排(抖音/淘宝/所有推荐)

**场景 & 难点**:内容池**上亿**,要在**几十毫秒**内选出用户最可能喜欢的几十个。一步到位不可能(亿级过复杂模型算不完)→ **漏斗式级联**。

**四级漏斗(公开量级)**:
| 阶段 | 输入→输出量级 | 模型/策略 | 目标 |
|---|---|---|---|
| **召回** | 亿 → 千(<50ms) | 多路召回(内容/协同/**向量**),模型简单、入口大 | 高**召回率**,别漏 |
| **粗排** | 千 → 百 | 轻量模型(如双塔打分) | 快速砍量 |
| **精排** | 百 → 几十 | 重模型(深度 CTR/多目标),用大量特征 | 高**精准**,定留存转化 |
| **重排** | 几十 → 几十 | 业务策略:**去已读/去重/打散/多样性/新鲜度** | 体验与生态 |

**多路召回**:内容召回 + 协同过滤 + **Embedding 向量召回** 并行,各出一批再合并去重。方便加新策略(主路 + 旁路)。

**⟵ 反查八股**:
- **级联漏斗 = 分层过滤思想**,和秒杀"分层拦截流量"同构(见 [05 案例 1](05-cases-ecommerce-seckill.md))。
- **每层延迟预算**:召回 <50ms → 天然排斥慢模型 → **这就是"为什么 LLM 进不了在线召回"的工业铁证**(见案例 4 + 你的 thesis)。
- **并行召回**:多路 `并发` 执行再聚合(见 [03 并发](03-concurrency-runtime.md))。
- **缓存**:用户/物品特征、召回结果缓存(见 [02 缓存](02-mysql-redis.md))。

**面试追问**:
- "为什么要分这么多层,不能一个模型搞定?" → 精度与算力的权衡:亿级只能过简单模型(召回),逐层缩小候选、逐层加重模型,把算力花在刀刃(精排几十~百个)。
- "召回评价指标?" → 召回率(别漏)、多样性;精排看 AUC/CTR/转化。

**连接 ShopMesh**:我的 `hybrid_search(向量+硬过滤召回) → ranker(多目标加权=粗/精排) → 后处理(重排/去重)` **就是这套级联漏斗的最小版**;我甚至能说"我把这套原理反过来用在秒送:确定性召回+确定性排序,LLM 不进召回链"。

## 案例 3 · 向量召回 / 双塔模型 / ANN(HNSW)(直连你的项目)

**场景 & 难点**:传统标签/协同召回覆盖不了语义(用户想要"适合夏天的清爽面霜"),要**按语义相似度**从亿级物品里找最近邻,还得毫秒级。

**方案:双塔 + ANN**:
- **双塔模型**:用户塔、物品塔两个独立 DNN,各自把特征编码成 **Embedding 向量**;相似度(内积/cosine)= 匹配度。
- **离线 + 在线拆分**:**物品向量离线预计算**(量大、不常变)灌进向量索引;**用户向量在线实时算**(一次)→ 拿去 ANN 检索。**又是"离线富化 + 在线毫秒"**。
- **ANN(近似最近邻)**:精确最近邻在亿级上太慢 → 用近似换速度。常见:IVF(倒排聚类)、PQ(乘积量化压缩)、**HNSW(分层可导航小世界图)**。
- **HNSW 一句话**:"邻居的邻居也是邻居",由疏到密建多层图,上层跳远、下层精找,查询 ~O(log N),召回率高、速度快 → 现在主流。

**⟵ 反查八股**:
- **HNSW / ANN / Embedding**:向量检索核心(你项目 Qdrant 就用 HNSW;原理见项目文档 [interview-prep §4 Q11](../interview-prep.md))。
- **bi-encoder(双塔,快)vs cross-encoder(精排 reranker,准但慢)**:双塔召回 + cross-encoder 精排的分工(见项目 reranker 设计)。
- **离线预计算 + 在线轻量**:降在线延迟的通用手段(见案例 2/4)。
- **内联过滤 vs 后过滤**:向量召回叠加硬条件时,下推过滤避免召回塌陷(**你项目的 Qdrant HNSW 内联过滤 / geo 下推**就是这个)。

**面试追问**:
- "双塔为什么不用 cross-encoder 召回?" → cross-encoder 要把 (user,item) 拼一起逐对算,亿级算不完;双塔可**预计算物品向量 + ANN**,才能在线毫秒。
- "ANN 会漏真正最近的吗?" → 会(近似),用召回率衡量;调参(HNSW 的 efSearch/M)权衡速度与召回。

**连接 ShopMesh**:**这题我有真代码**——Qdrant HNSW + BGE-M3 embedding 混合检索、payload 内联过滤避免后过滤召回损失、秒送里 geo/时效硬约束下推。面试到向量召回我能从原理讲到落地。

## 案例 4 · LLM 在推荐里到底放哪(淘宝 RecGPT,你 thesis 的工业锚点)

**场景 & 难点**:大模型强在语义理解/意图推理,但**单次推理几百 ms~秒级**,进不了毫秒级在线召回/排序。那 LLM 在十亿级推荐里怎么用?

**RecGPT 方案(阿里,2025 淘宝首猜全量上线,公开数据点击双位数增长)**:
- **闭环**:用户兴趣挖掘 → 商品标签预测 → 商品召回 → 推荐解释生成,每步用 LLM 做**意图推理与语义理解**。
- **关键工程:离线富化**。为避免"实时给每个 user-item 生成解释"的算力爆炸,**离线**为所有"兴趣-品类"对生成解释、存进 **lookup table**;在线按用户兴趣+品类**查表**取预生成结果。
- **三塔召回(user-product-label)**:LLM 生成的**细粒度标签**作为语义信号,与传统协同信号**融合**联合优化。

**⟵ 反查八股 / 核心判断**:
- **这就是"LLM 离线富化 + 传统召回在线毫秒服务"的活教材**——和你简历那句"我清楚为什么不在毫秒级 feed 里塞 LLM"**完全一致**。
- **空间换时间 / 预计算 + 查表(lookup table)**:典型缓存/预计算思想(见 [02 缓存](02-mysql-redis.md))。
- **级联架构里 LLM 只做离线信号增强,在线仍是轻量召回排序**(见案例 2)。

**面试追问(这题答好=直接展示你的判断力)**:
- "为什么不让 LLM 在线直接推荐?" → 延迟(百 ms~秒 vs 召回 50ms)、算力成本(十亿 user×亿 item)、稳定性。→ **LLM 离线产语义信号/解释,在线查表 + 轻量模型。**
- "那 LLM 在推荐里的价值是什么?" → 冷启动/长尾语义理解、意图推理、可解释性、打破信息茧房;**不是替代召回排序,是增强特征与理解层**。

**连接 ShopMesh**:**这题几乎是我项目的中心思想。** 我在导购/秒送里就是这么划界的:确定性 recsys 做召回排序(在线毫秒),LLM 只在能容忍秒级、且多步推理有增量的**对话/组单**层。RecGPT 正好印证了这条边界在十亿级生产里也成立。

## 案例 5 · Feed 翻页一致性:去重 / 已读 / 不重不漏

**场景 & 难点**:边刷边有新内容插入,用传统 `offset/limit` 分页会**重复或漏**(数据在动,页码错位);还要"刷过的不再出"。

**方案**:
- **游标分页(cursor / seek)**:用上一页最后一条的**时间戳/ID/分数**作为游标 `where score < last_score limit N`,而非 offset。稳定、且**避免大 offset 深分页**性能问题。
- **已读去重**:用户已读集合用 **布隆过滤器**(省内存,判"一定没读过/可能读过")或 Redis Set;重排层过滤已读。
- **多样性打散**:重排层把同类/同作者内容打散,避免连刷同质。

**⟵ 反查八股**:
- **布隆过滤器**:判存在、省内存、有假阳(见 [02 §5 缓存穿透](02-mysql-redis.md) 也用它)。
- **游标分页 vs offset 深分页**:深分页 `limit 100000,10` 要扫十万行 → 游标/延迟关联优化(见 [02 §9](02-mysql-redis.md))。
- **Redis Set / Bitmap** 存已读。

**面试追问**:
- "为什么不用 offset 分页?" → 数据动态插入导致重复/遗漏 + 大 offset 慢。
- "布隆过滤器假阳会漏推吗?" → 会有极小概率"没读却判读过"→ 少推一条,可接受;不能用在"必须精确"的场景。

**连接 ShopMesh**:我是对话式即时检索,没有长列表翻页;但知道 feed 场景要用游标 + 布隆去重。

## 案例 6 · 实时热榜 / 排行榜(热搜、热销、热门)

**场景 & 难点**:实时统计"最近 1 小时最热"并排序,高并发读写榜单。

**方案**:
- **Redis ZSet(有序集合)**:member=物品、score=热度;`ZINCRBY` 累加热度、`ZREVRANGE` 取 Top-N,天然排序、O(logN) 更新。
- **时间窗口**:滑动窗口热度(分桶按分钟,过期桶淘汰)或带时间衰减的 score(读时衰减)。
- **抗热点**:榜单是超级热点 key → 本地缓存 + 短 TTL(见案例/多级缓存)。

**⟵ 反查八股**:
- **Redis ZSet 底层 skiplist**:为什么能高效范围/排序(见 [02 §1](02-mysql-redis.md))。
- **滑动窗口**:限流也用它,这里用于时间窗口热度统计(见 [04 §6](04-distributed-mq-design.md))。
- **读时衰减**:避免写时全量刷新(见项目记忆衰减设计 / [03](03-concurrency-runtime.md))。

**面试追问**:"千万级榜单 ZSet 单 key 太大怎么办?" → 分片(按品类/地域拆多个 ZSet)+ 定期合并 Top-N。

**连接 ShopMesh**:我的**读时指数衰减记忆**和这里的"带时间衰减的热度 score"是同一手法(读时算、不写时刷)。

## 案例 7 · 推荐服务的高可用:缓存 / 降级 / 兜底

**场景 & 难点**:推荐链路长(召回→排序→特征),任一环节抖动都会拖慢/拖垮;但推荐**不能白屏**。

**方案**:
- **多级缓存**:特征、召回结果、用户画像缓存,降低对下游/模型服务的冲击。
- **降级兜底**:精排模型超时/挂了 → 退到**粗排结果**;召回挂了 → 退到**热门榜/运营兜底池**;绝不返回空。
- **超时控制 + 熔断**:每层设超时,慢就用已有结果;依赖故障熔断,防雪崩。
- **特征读取**:特征平台(Feature Store)高并发 KV 读,缓存 + 批量拉取。

**⟵ 反查八股**:
- **降级 / 熔断 / 超时**:高可用三板斧(见 [04 §6](04-distributed-mq-design.md))。
- **多级缓存**(见 [05 案例 6](05-cases-ecommerce-seckill.md))。
- **舱壁隔离**:各依赖线程池隔离防互相拖垮。

**面试追问**:"推荐降级到热门榜,个性化没了用户会不会跑?" → 短时降级保可用 > 无结果;比"转圈/白屏"体验好得多,恢复后再切回。

**连接 ShopMesh**:我的 agent 也有降级思路——LLM 网关不可用时**退到确定性检索**返回结果,不让整个对话失败。
