# 第一部分:计算机网络

## 1. 网络分层
- **OSI 七层**:物理、数据链路、网络、传输、会话、表示、应用。
- **TCP/IP 四层**:网络接口层、网络层(IP)、传输层(TCP/UDP)、应用层(HTTP/DNS/…)。
- 记忆锚:数据自上而下**封装**(加头)、自下而上**解封装**。每层职责:网络层 IP **选路寻址**,传输层 **端到端可靠/复用(端口)**,应用层业务语义。

## 2. TCP vs UDP(必考)
| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接(握手) | 无连接 |
| 可靠 | 可靠(确认/重传/有序) | 不可靠、尽力而为 |
| 头部 | 20~60 字节 | 8 字节 |
| 传输 | 字节流 | 数据报(保留边界) |
| 场景 | HTTP/文件/邮件 | DNS/视频/直播/游戏/QUIC |
- **为什么 UDP 快**:无握手、无拥塞控制、头小。视频宁可丢帧也不要卡顿 → UDP。

## 3. 三次握手(建立连接)
1. C→S:SYN(seq=x)—— 我要连,初始序号 x
2. S→C:SYN+ACK(seq=y, ack=x+1)—— 同意,我的序号 y
3. C→S:ACK(ack=y+1)—— 收到

**为什么 3 次不是 2 次?**
- 要**双向确认收发能力**。2 次只能确认「C→S 通」,不能确认「S→C 通」。
- 防**历史失效连接**:一个早已超时的旧 SYN 到达 S,若 2 次握手 S 就建连并发数据,浪费资源;3 次让 C 能拒绝(ACK 不认)。

**为什么不是 4 次?** SYN 和 ACK 可以合并成一个包,3 次够了。

## 4. 四次挥手(关闭连接)
1. C→S:FIN —— 我没数据要发了
2. S→C:ACK —— 知道了(此时 S 可能还有数据要发 → **半关闭**)
3. S→C:FIN —— 我也发完了
4. C→S:ACK —— 好,主动方进入 **TIME_WAIT**

**为什么 4 次?** 关闭是全双工的,S 收到 FIN 后 ACK 是立即的,但它自己的数据可能还没发完,所以 FIN 要等发完再单独发 → ACK 和 FIN 拆成两步。

**TIME_WAIT(2MSL)为什么存在?**
- ①保证**最后一个 ACK 能重传**(若 S 没收到 ACK 会重发 FIN,C 还在 TIME_WAIT 能应答)。
- ②让**本连接的旧包在网络中消散**,避免影响下一个相同四元组的连接。
- 大量 TIME_WAIT 是主动关闭方(常是服务器短连接/客户端)的常见问题,可 `SO_REUSEADDR`、连接复用缓解。

**其它状态**:`CLOSE_WAIT` 堆积 = 对端关了但你的应用没 `close()`(代码 bug)。

## 5. TCP 如何保证可靠传输(高频)
- **序号 + 确认(ACK)**:每个字节有序号,累计确认。
- **超时重传**(RTO 动态计算)+ **快速重传**(收到 3 个重复 ACK 立即重传,不等超时)。
- **滑动窗口**:接收方通告 `rwnd`,实现**流量控制**(不让发太快撑爆接收缓冲)。
- **拥塞控制**(控制网络不拥堵,`cwnd`):
  1. **慢启动**:cwnd 从 1 指数增长,到 ssthresh。
  2. **拥塞避免**:超过阈值后线性增长(加法增大)。
  3. **快重传 + 快恢复**:收到 3 个重复 ACK,ssthresh=cwnd/2,cwnd 减半后线性增(乘法减小),不回到 1。
- 一句话:**流控看接收方,拥塞控制看网络**;实际发送窗口 = min(rwnd, cwnd)。

## 6. HTTP
- **方法**:GET(查、幂等、可缓存)、POST(改、非幂等)、PUT(全量更新、幂等)、DELETE、PATCH(局部)。
- **GET vs POST**:语义(查 vs 改)、参数位置(URL vs body)、幂等性、可缓存性、长度限制(GET 受 URL 限)。本质是语义约定,底层都能带 body。
- **状态码**:2xx 成功(200/201/204),3xx 重定向(301 永久/302 临时/304 协商缓存命中),4xx 客户端(400/401/403/404/429),5xx 服务端(500/502/503/504)。
- **版本演进**:
  - 1.0:短连接(每请求建连)。
  - 1.1:**长连接(keep-alive)**、管线化(有队头阻塞)、Host 头、分块传输。
  - 2.0:**二进制分帧**、**多路复用**(一个连接并发多请求,解决 HTTP 层队头阻塞)、头部压缩 HPACK、服务端推送。**但仍受 TCP 层队头阻塞**(丢包时)。
  - 3.0:基于 **QUIC(UDP)**,彻底解决 TCP 队头阻塞、0-RTT 建连。

## 7. HTTPS / TLS(必考)
- **为什么**:HTTP 明文,防窃听/篡改/冒充。
- **组合拳**:非对称加密(RSA/ECDHE)解决**密钥分发**,对称加密(AES)负责**数据传输**(快),证书解决**身份认证**。
- **TLS 握手(简化,RSA 版)**:
  1. C→S:Client Hello(支持的加密套件、随机数)
  2. S→C:Server Hello(选定套件、随机数)+ **证书**(含公钥)
  3. C:验证证书链(是否 CA 签发、域名、有效期),生成 pre-master,用**服务器公钥加密**发过去
  4. 双方用三个随机数算出**对称会话密钥**,之后用对称加密通信
- 现代多用 **ECDHE**(前向安全:即使私钥泄露也解不了历史流量)。
- **证书链**:根 CA → 中间 CA → 域名证书,逐级签名;根 CA 内置在操作系统/浏览器。
- **中间人**:攻击者无合法证书 → 浏览器告警;所以别乱装根证书。

## 8. HTTP 缓存
- **强缓存**(不发请求,直接用本地):`Cache-Control: max-age=xxx`(优先)/ `Expires`。
- **协商缓存**(发请求问服务器变没变,没变返回 **304**):
  - `Last-Modified` / `If-Modified-Since`(秒级、有精度问题)
  - `ETag` / `If-None-Match`(内容指纹,更准,优先)
- 流程:先看强缓存命中?命中直接用;否则带协商头问,304 用本地、200 用新的。

## 9. Cookie / Session / Token / JWT
- **Cookie**:浏览器存的小数据,每次请求自动带上;有 `HttpOnly`(防 XSS 读)、`Secure`、`SameSite`(防 CSRF)。
- **Session**:状态存**服务端**,Cookie 存 sessionId。有状态 → 分布式要 session 共享(Redis)。
- **Token/JWT**:状态存**客户端**(JWT = header.payload.signature,服务端**验签**即可,无需存储)→ 天然适合分布式/无状态。缺点:**无法主动失效**(需黑名单)、载荷可见(别放敏感信息)。
- 你的项目:Java 用 RSA 签 JWT,Python 拉 JWKS 公钥验签 → **跨语言无状态信任**,正好能讲。

## 10. DNS 解析过程
浏览器缓存 → 系统 hosts/缓存 → 本地 DNS(递归解析器)→ 根域名服务器 → 顶级域(.com)→ 权威域名服务器 → 返回 IP。**递归查询**(你问本地 DNS)+ **迭代查询**(本地 DNS 问各级)。

## 11.(压轴)输入 URL 到页面显示全过程
1. **DNS 解析**域名→IP
2. **建立 TCP 连接**(三次握手;HTTPS 再 TLS 握手)
3. 浏览器发 **HTTP 请求**
4. 服务端处理(可能经 Nginx/网关/负载均衡→应用→DB/缓存)返回响应
5. 浏览器**解析渲染**(构建 DOM/CSSOM → 渲染树 → 布局 → 绘制),边解析边请求子资源(可命中缓存)
6. 关闭或复用连接
> 能顺带提"每步的优化点"(DNS 预解析、CDN、连接复用、缓存、Gzip、懒加载)= 加分。

# 第二部分:操作系统

## 1. 进程 vs 线程 vs 协程(必考)
- **进程**:资源分配的基本单位,独立地址空间;切换开销大(切页表/TLB)。
- **线程**:CPU 调度的基本单位,共享进程地址空间;切换比进程轻(不切地址空间);需同步。
- **协程**:用户态调度,由程序自己切换,**不陷入内核**,极轻量(栈小);一个线程可跑成千上万协程。适合 IO 密集高并发。
- 开销排序:进程切换 > 线程切换 >> 协程切换。

## 2. 进程间通信 IPC
管道(匿名/命名)、消息队列、**共享内存(最快,需同步)**、信号量(同步用)、信号(异步通知)、Socket(跨主机)。

## 3. 线程同步
互斥锁 mutex、信号量 semaphore(计数,可控 N 个)、条件变量(等待/通知,配合锁)、读写锁(读共享写独占)、自旋锁(忙等,适合临界区极短)。

## 4. 死锁(必考)
- **四个必要条件**:①互斥 ②持有并等待 ③不可剥夺 ④循环等待。
- **处理**:
  - 预防:破坏任一条件(如**一次性申请全部资源**破坏②;**资源有序申请**破坏④——最常用)。
  - 避免:银行家算法(判断是否进入不安全状态)。
  - 检测 + 恢复:资源分配图找环,杀进程/回滚。
  - 鸵鸟策略:忽略(概率低时)。

## 5. 进程调度算法
FCFS、SJF(短作业优先,可能饿死长作业)、优先级、**时间片轮转 RR**、多级反馈队列(综合,现代 OS 用)。

## 6. 内存管理(必考)
- **虚拟内存**:每个进程独立的连续虚拟地址空间,由 MMU + 页表映射到物理内存。好处:隔离、比物理内存大(换页)、共享。
- **分页**:固定大小页(如 4KB),解决外部碎片;有内部碎片。**分段**:按逻辑段(代码/数据/栈),便于共享保护;有外部碎片。现代多用**段页式**。
- **TLB**:页表缓存,加速地址翻译。
- **缺页中断**:访问的页不在内存 → 陷入内核 → 从磁盘换入(可能先换出一页)。
- **页面置换算法**:OPT(最优,理论)、FIFO(有 Belady 异常)、**LRU**(最近最少使用,常考)、**Clock/二次机会**(LRU 近似,实现便宜)、LFU。
- **抖动(thrashing)**:频繁缺页换页,CPU 利用率暴跌 → 工作集模型控制多道程度。

## 7. 用户态 / 内核态、系统调用
- CPU 有特权级;操作硬件/内存等敏感操作只能内核态。
- **系统调用**:用户程序请求内核服务(read/write/fork)→ 软中断陷入内核 → 有**上下文切换开销**,所以减少系统调用次数(如批量、零拷贝)是优化手段。

## 8. IO 模型 + 多路复用(后端必考)
**五种 IO 模型**:阻塞 IO、非阻塞 IO(轮询)、**IO 多路复用(select/poll/epoll)**、信号驱动 IO、异步 IO(AIO)。
- **同步 vs 异步**:数据拷贝阶段是否由内核完成后通知你(异步 = 内核全干完再叫你)。
- **阻塞 vs 非阻塞**:发起调用后要不要立刻返回。

**select / poll / epoll(重点)**:
| | select | poll | epoll |
|---|---|---|---|
| fd 上限 | 1024 | 无(链表) | 无 |
| 效率 | 每次 O(n) 遍历 + 拷贝全量 fd | 同 select(无上限) | **O(1) 就绪回调**,只返回就绪 fd |
| 数据结构 | 位图 | 数组 | 红黑树 + 就绪链表 |
- epoll 三函数:`epoll_create`、`epoll_ctl`(增删改监听)、`epoll_wait`(取就绪)。
- **LT(水平触发)**:只要有数据就一直通知(默认,不易漏)。**ET(边缘触发)**:状态变化才通知一次,必须一次读干净(配非阻塞循环读),性能更高但难写。
- **Reactor 模式**:多路复用 + 事件分发,是 Nginx/Redis/Netty 的基础。

## 9. 零拷贝(高频进阶)
- 传统 `read+write` 发文件:磁盘→内核缓冲→**用户缓冲→内核 socket 缓冲**→网卡,4 次拷贝 + 4 次上下文切换。
- **零拷贝**:`mmap`(省一次用户态拷贝)、`sendfile`(内核内直接传,不进用户态)、`splice`。Kafka/Nginx 高吞吐靠它。
