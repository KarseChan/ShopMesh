# 简历叙事 & 面试话术(ShopMesh 智能导购 Agent)

> 给你自己看的。简历怎么写、面试怎么讲、以及被追问时怎么答。核心原则:**诚实 + 突出工程判断,而非堆功能。**

---

## 一句话定位

> 基于 LangGraph 的对话式导购 + 交易 Agent 系统:自然语言 → 意图路由 → ReAct agent(工具:混合检索/多目标排序/购物车/下单)→ 推荐与购买闭环。**重点不是功能多,而是我对它做的架构收敛、延迟优化和生产级交易设计。**
>
> 之后在同一套 agent 上扩了一个**对话式即时配送(秒送点单)垂类**,用来证明我最想展示的一个判断:**哪些该交给确定性 recsys、哪些才该交给 LLM agent**——这条边界本身就是最值钱的东西。

---

## 简历要点(挑 3–4 条,带数字)

- 设计并实现对话式导购 Agent:**确定性意图路由 + 每意图独立 ReAct agent**(独立 prompt/工具子集/迭代预算),工具化封装混合检索(Qdrant 向量 + payload 预过滤)与多目标排序。
- **架构收敛**:将并存的 5 套执行编排收敛为单一主路径,删除死代码;基于领域判断主动移除 LLM 动态 DAG 编排(封闭意图空间不需要),降低不确定性与维护成本。
- **端到端延迟优化 116s → 22–39s**(单一慢推理模型下):把在线 LLM 调用从 8 次降到 1–2 次(逐商品文案/总结确定性化、规则快路径抽实体、收敛冗余工具调用)。
- **生产级 Agent 交易子系统**:LLM 只编排、不自主执行支付;下单/支付走确定性代码 + 人工确认闸门 + 服务端二次校验;库存 Redis 原子预占防超卖、幂等键防重复扣款、**支付只信 HMAC 验签 webhook**、Celery 超时对账。
- 搭建**推荐质量 Eval**,用可复现指标(预算/品类/场景命中率)驱动改进。
- **垂类扩展(对话式秒送点单)+ recsys/agent 边界判断**:在同一 agent 上扩即时配送垂类,明确划边界——毫秒级 feed 是确定性 recsys(**不塞 LLM**),agent 只做对话式约束求解 + 组单/下单编排;把 **geo 半径 / 营业中 / 时效 硬约束下推到向量库(Qdrant)预过滤**(复用"场景白名单下推"手法),让闲置的 `delivery_minutes` 变成一等排序信号(时效优先 profile);**复用交易范式、零新增迁移**接通下单→支付→履约状态机;LLM 只用在"预算内凑单(assemble_meal)"这类多步权衡处。秒送每层硬约束都有可复现 eval(送达可行率/时效达成率/预算命中/凑单用满率)。

## 三个能讲深的技术点(面试主攻)

### 1. "为什么砍掉 DAG 多智能体编排?"(架构判断)
- 导购意图空间是**封闭已知**的(搜/推、详情/比价、澄清)。封闭意图 → **确定性路由**是正解。
- LLM 动态拆 DAG 换来的灵活性用不上,却多一次 LLM 调用 + JSON 解析失败点 + 环检测,还 0 测试、有过循环 bug。
- **"我评估后认为该场景不需要 DAG,砍掉以收敛架构"——主动暴露并反思过度设计,是加分项。**

### 2. "系统为什么慢,你怎么优化的?"(延迟)
- 先**实测定位**:profiler 拆出 116s = 8 次串行 LLM(preprocess 抽实体 20s + agent 迭代 + 逐商品文案 47s + 总结 14s)。
- 根因:网关只有一个慢推理模型(单次 7–15s),**换不了模型 → 只能减少调用次数**。
- 对照生产级(淘宝 RecGPT:LLM 离线富化 + 传统召回在线服务毫秒级),把能确定性/预计算的都移出在线路径。
- 结果:逐商品文案用排序器的确定性理由(去 3 次 LLM)、总结模板化(去 1 次)、规则快路径抽实体(去 1 次,20s→2.6s)、收敛冗余工具调用。**116s → 22–39s。**

### 3. "Agent 怎么做购买而不出资损?"(交易设计)
- **核心闸门**:LLM 会幻觉、会被 prompt injection,所以**绝不让 LLM 自主花钱**。
- 分层:读(搜索)=agent 自由;写(购物车,可撤销)=agent 可调;敏感(下单/支付)=**必须人工确认 + 确定性代码执行**,SENSITIVE 工具在执行器被拦截。
- 工程点:库存原子 DECR 防超卖、下单幂等键、**支付只信验签 webhook(伪造回调实测被拒)**、Celery 超时取消 + 释放库存。
- 支付**不接真实资金**,用沙箱走和真实一样的验签链路。

### 4. "秒送这个垂类你怎么设计的?"(recsys/agent 边界 —— 最新、最能体现判断)
- **一句话边界**:*核心秒送推荐我用确定性 recsys(生产就是这么做);agent 只负责对话式约束求解与下单编排。我清楚为什么不在毫秒级 feed 里塞 LLM。*(和延迟那点同一个 thesis:LLM 进不了毫秒在线路——我的网关 16s 就是证据。)
- **逐层归属**:首页/列表 feed(高 QPS)= 确定性 recsys,**刻意不碰**;就近召回 + 硬过滤(geo/营业中/时效/预算)= 确定性代码,**下推到 Qdrant 预过滤**(HNSW 只遍历可行门店,避免事后过滤打空)+ haversine 精算距离回填;多目标排序 = 确定性 ranker,新增距离/时效/配送费维 + 时效优先 profile;自然语言→结构化多约束 = **规则快路径优先**(能判定就不调 LLM);"预算内凑单/再来一单" = agent 编排,**只有 assemble(模糊口语→多约束→多菜权衡)才真用 LLM ReAct**,recall/reorder 是单步可判定 → 确定性。
- **四阶段落地**:①就近约束检索(schema+mock+geo 下推+时效排序,命令行验证)②点单闭环(**复用**购物车/订单/支付,零新迁移,加履约状态机 备餐→配送中→已送达)③agentic(reorder 历史重放 + assemble 预算背包,LLM 只在 assemble 编排)④前端门店卡片+菜单点单。每步都先做确定性内核 + eval,再接 LLM/前端。
- **为什么这条最值钱**:同时体现"懂产业"(美团 2025 小美/淘宝问问都印证 agent 只在对话层、feed 仍是级联 recsys)+ "有判断"(知道哪里**不该**用 LLM)。**加它是强化差异化,不是堆功能。**

## 会被追问怎么答(诚实要点)

- **"这些优化(hooks/compact/recovery)是你原创的吗?"** → 诚实:参考了 Claude Code 的机制并移植,关键是我**理解每一项为什么存在**并判断哪些适用(例:hooks 系统我查出其实从未接线、是空转的,没当"已完成功能"讲)。
- **"双语言/RabbitMQ/Traefik 有必要吗?"** → 承认早期过度设计:"对这个业务规模偏重,如果重来我会先用单语言 + 直连,等真有多团队/异步需求再拆。" **主动反思比被问穿强。**
- **"天花板在哪?"** → 这是"能把已知模式落地成有生产意识的 agent 系统",不是"提出新架构"。别往前沿吹。
- **"秒送是真跑通的还是玩具?"** → 诚实:门店/经纬度/ETA 都是 **mock**,不接地图 API、不做真实骑手调度(和沙箱支付同思路——走对的架构、不接真实基建)。但**约束下推、时效排序、下单→支付→履约状态机、凑单**都是真代码 + 有可复现 eval 指标。价值在**边界判断和范式复用**,不在真实履约系统。
- **"为什么 recall/reorder 不用 LLM,只有 assemble 用?"** → recall(就近召回)是可判定的约束求解、reorder(再来一单)是历史重放,规则更快更稳、还能进 CI;assemble(模糊口语→多约束→预算内多菜权衡)才是多步推理,LLM 有增量。**知道哪里不该用 LLM,和哪里该用,一样重要。**
