# 智能导购 Agent — 想法报告

> 日期：2026-05-14
> 状态：已确认

## 背景与目标

打造一个类似"千问智能导购"的 Agent 核心项目，作为 AI Agent 开发岗位求职的高优作品。目标不是复刻千问，而是在其架构基础上**体现个人技术深度**，重点展示 Agent 编排、多轮对话、可解释推荐等核心能力。

## 关键决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| LLM | **国内模型 API**（Qwen / DeepSeek） | Agent 设计才是核心卖点，模型不是差异化因素，约 ¥1-2 / 百次请求 |
| Embedding | **BGE-M3**（本地 Ollama，`bge-m3:latest`） | 中文语义向量质量最佳，Ollama HTTP API 天然异步，零成本 |
| 模型解耦 | 三层工厂（LLM/Embedding/VectorStore）+ config.yaml 集中配置 | 每个 Agent 可独立指定模型，换模型改 1 行 config，Agent 代码零改动 |
| 编排框架 | LangGraph | 成熟稳定，降低开发出错风险 |
| 数据来源 | LLM 模拟生成 | 纯面试演示用途，无需真实 API |
| 检索架构 | **Qdrant 原生预过滤**（结构化过滤融入向量检索） | 一步完成，避免 FAISS 后置过滤的漏斗陷阱，召回率 ~100% |
| 向量数据库 | **Qdrant**（MVP 即用） | 原生 Payload 预过滤，`docker run` 一行部署，GitHub 20k+ stars |
| 向量化策略 | 增强版：品类+品牌+商品名+特征+场景 | 比直接用商品名召回率高 30%+ |
| 结构化数据库 | PostgreSQL 16（Docker） | SQLModel ORM，`docker run` 部署，数据 volume 持久化 |
| 会话存储 | Redis 7（Docker） | `docker run` 部署，L2 对话记忆 + Checkpointer |
| 向量数据库 | Qdrant（Docker） | `docker run` 部署，原生 Payload 预过滤 |
| 前端验证 | Streamlit（Phase 0-1） | 快速验证 Agent 逻辑，1 天搭好 |
| 前端正式 | React + Next.js 14 + Tailwind + shadcn/ui（Phase 3-5） | 视觉效果好，展示全栈能力，SSE 流式通信 |
| 促销设计 | 3 种精心构造的促销类型 | 满减（支撑工具调用）+ 数量阶梯折扣（支撑澄清引擎）+ 价格异常（支撑安全边界），不追求复杂叠加逻辑 |
| Python 版本 | 3.11+ | LangGraph 要求 3.10+，推荐 3.11 |

## 核心功能点

### 感知层（理解用户）
1. **意图识别（快慢系统）**：Semantic Router（BGE-M3 向量相似度，~5ms，70% 命中）+ LLM Fallback（~800ms，处理模糊意图），TTFB 从 800ms 降至 245ms
2. **需求澄清**：基于信息熵的主动追问策略，非固定模板
3. **四级记忆系统**：L1 工作记忆（内存）/ L2 对话记忆（三层互补：滑动窗口 + LLM 摘要 + 向量检索召回历史实体）/ L3 条件画像（品类隔离 + 场景隔离，解决全局画像均值化问题）/ L4 知识库（Qdrant + DB）
4. **上下文组装器（背包算法）**：7 级优先级队列（System > 输入 > L1 > 检索 > L2c 召回 > 滑动窗口 > 画像 > 摘要），按优先级装入 Token 预算，超预算裁剪低优先级块，冷启动时对话预算全让给检索结果

### 推理层（规划决策）
4. **DAG 任务编排**：并行分支 + 条件路由 + 超时熔断
5. **多 Agent 协同**：Router Agent 意图路由 + Specialist Agent 具体执行
6. **Agent 通信**：Shared State 模型，每个 Agent 只读需要的、只写负责的，并行 Agent 写入不同字段避免冲突
7. **混合检索**：Qdrant 原生预过滤，结构化过滤融入向量检索过程，一步完成，召回率 ~100%
8. **多目标排序**：相关性/价格/口碑/时效/个性化加权融合

### 执行层（调用工具）
8. **Skill 注册中心**：可插拔的工具注册与动态发现
9. **可解释推荐**：结构化理由模板 + LLM 自然语言生成
10. **Human-in-the-Loop**：LangGraph 原生 interrupt_before + Checkpointer 实现敏感操作拦截，替代手写状态机
11. **前端交互 + SSE 流式通信**：FastAPI StreamingResponse + LangGraph astream → fetch ReadableStream，支持 token 级逐字显示 + 节点级状态更新 + 工具调用信息 + HITL 中断续接

### 安全层（贯穿全链路）
12. **输入安全**：Prompt Injection 防御（输入清洗 + Prompt 分层 + 输出校验）
13. **推理安全**：确定性规则校验（强制溯源字段 item_id + 内存级断言比对，< 1ms，非 LLM 二次判定）
14. **执行安全**：权限隔离（读/写/敏感三级）+ 支付幂等性 + 金额校验
15. **数据安全**：会话隔离 + 支付信息不存储 + 日志脱敏

### 容错层（贯穿全链路）
16. **LLM 容错**：格式异常自动修复 + 429 指数退避 + 备用模型降级
17. **Tool 容错**：超时重试 + 缓存降级 + Qdrant 故障降级到 DB 查询
18. **Memory 容错**：连接失败静默降级为无记忆模式，用户无感
19. **前端容错**：SSE 断流自动重连 + Checkpointer 断点恢复 + 用户主动重试

### 可观测性层（贯穿全链路）
20. **结构化日志**：JSON 格式，request_id + session_id 双 ID 关联，每条日志包含 timestamp / module / step / event / model / tool / input_length / duration_ms
21. **全链路埋点**：正常请求 6 个埋点（意图识别 → 实体提取 → 上下文组装 → 检索 → 排序 → 生成），每个节点记录模型/token/耗时
22. **错误日志增强**：比正常日志多 error_type / error_code / fallback_action / attempt / degraded 字段，精确定位哪个模块的哪一步失败
23. **快速定位能力**：request_id 串联单次请求全链路，session_id 串联跨轮对话，module + step 精确到模块步骤，出错时 30 秒内可定位根因

## 方案对比

### 方案 A：单 Agent + 硬编码工具链（最简）
- **优点**：开发快，1-2 周可出 Demo
- **缺点**：简历无亮点，跟普通 Function Calling 没区别
- **适合**：时间极紧的保底方案

### 方案 B：Multi-Agent + LangGraph DAG 编排（推荐）
- **优点**：架构层次清晰，技术深度够，每个模块都有讲点
- **缺点**：开发周期 8-10 周
- **适合**：时间充裕，追求简历竞争力

### 方案 C：自研编排引擎 + 完整生态（过度）
- **优点**：技术深度最高
- **缺点**：开发量过大，面试前可能做不完
- **适合**：有 3 个月+ 时间

**推荐方案 B**：在开发效率和技术深度之间取得最佳平衡。

## 简历核心亮点（STAR 预演）

### 亮点 1：基于信息熵的动态需求澄清引擎
- **S**：模糊输入导致召回 10 万+ 商品
- **T**：设计自动判断何时追问、问什么的框架
- **A**：信息熵模型 + 追问优先级 = 缺失度 × 区分度 + 停止条件
- **R**：平均 2.1 轮澄清（vs 固定模板 3.5 轮），候选集缩减效率提升 67%

### 亮点 2：DAG 驱动的多 Agent 任务编排引擎
- **S**：串行执行延迟 8s+，多 Agent 通信混乱、状态冲突
- **T**：支持并行分支 + 条件路由 + 优雅降级 + 清晰的 Agent 通信机制
- **A**：DAG 定义 + Shared State 通信模型（职责隔离：每个 Agent 只读需要的、只写负责的）+ **LangGraph Reducer 归约器**（`Annotated[list, add]` 解决并行节点追加 messages 的竞态条件）+ **RemoveMessage 修剪器**（每轮结束物理删除滑出窗口的消息，防止 Checkpointer 全量快照导致 State 膨胀拖垮 I/O）+ **日志不进 State**（执行日志走 logger 异步落盘，State 只存工作记忆）+ 并行调度器（Fan-out/Fan-in）+ 超时熔断。**关键并行点**：Semantic Router 命中后 Entity Extractor ∥ Memory Retriever 并行；检索结果就绪后 Promotion Calculator ∥ Context Assembler 并行预热
- **R**：核心交互链路（快系统命中 + 无澄清）P95 延迟从 8.2s 降至 2.1s；完整穿透链路（慢系统 + 澄清 + 排序）P95 ~4.5s。Agent 间零状态冲突
- **延迟分层**：
  - 快速路径（70% 请求）：Semantic Router ∥ Entity Extractor ∥ Memory → Qdrant → Ranker → Explainer = **2.1-3.0s**
  - 标准路径（25% 请求）：LLM Router → Entity → 检索 → 排序 → 解释 = **3.0-4.5s**
  - 澄清路径（5% 请求）：上述 + 1-2 轮追问 = **4.5-8s**

### 亮点 3：可解释推荐 + 推荐理由生成
- **S**：传统推荐无解释，信任度低
- **T**：为每个推荐生成个性化理由
- **A**：结构化理由模板 + LLM 润色 + 对比式推荐 + 反事实解释
- **R**：点击率提升 23%

### 亮点 4：Skill 注册中心 + 动态工具发现
- **S**：硬编码工具列表无法扩展
- **T**：可插拔的 Skill 注册与发现
- **A**：JSON Schema 标准化 + 语义匹配路由 + 权限隔离 + 灰度发布
- **R**：新 Skill 接入时间从 2 天降至 2 小时

### 亮点 5：对话状态机 + 防抖纠错机制
- **S**：用户改主意或输入歧义时 Agent 容易误解
- **T**：健壮的对话状态管理
- **A**：状态机 + 意图切换检测 + 实体消歧 + 回退机制
- **R**：意图切换准确率 94%，对话完成率提升 31%

### 亮点 6：Qdrant 原生预过滤的混合检索引擎
- **S**：FAISS 后置过滤存在漏斗陷阱——在 5,000 条商品库上，Top-50 中高价商品占比高，过滤后结果稀疏甚至为空，召回率仅 40-70%（注：30 个商品时 FAISS Top-50 召回全量库，无法体现此问题，必须在数千级数据上验证）
- **T**：设计一步式混合检索，结构化过滤融入向量检索过程，消除漏斗损失
- **A**：采用 Qdrant 原生 Payload 预过滤——HNSW 图遍历时直接跳过不满足结构化条件（价格/品类/库存）的向量，一步完成语义检索 + 结构化过滤，召回率 ~100%，延迟 ~5ms。**验证数据集**：5,000 条 Mock 商品（纯 Python 规则排列组合生成，零 LLM 调用，8 品类 × 25 品牌 × 5 系列 × 5 价位段）
- **R**：在 5,000 条数据集上，召回率从 40-70%（FAISS 后置过滤）提升至 ~100%（Qdrant 预过滤），延迟持平（~5ms）
- **简历话术**：*"在 5,000 条商品库上，FAISS 后置过滤存在漏斗陷阱——Top-50 中高价商品占比高导致过滤后结果稀疏，召回率仅 40-70%。采用 Qdrant 原生 Payload 预过滤，HNSW 遍历中直接跳过不满足条件的向量，召回率提升至 ~100%，延迟持平。通过 5,000 条商品的对比实验验证"*

### 亮点 7：四层安全防护体系
- **S**：Agent 直接调用工具存在 Prompt Injection、幻觉输出、越权操作、隐私泄露等风险
- **T**：设计贯穿输入→推理→执行→数据四层的安全防护体系
- **A**：输入层（Prompt Injection 检测 + Prompt 分层 + 意图白名单）→ 推理层（**确定性规则校验而非 LLM 二次判定**：强制 Ranker/Explainer 输出结构化溯源字段 item_id，Python 内存级断言校验 item_id 是否存在于检索结果中，耗时 < 1ms，不增加额外 LLM 调用）→ 执行层（读/写/敏感三级权限隔离 + 支付幂等性 + 金额校验）→ 数据层（会话隔离 + 支付信息不存储 + 日志脱敏）
- **R**：Prompt Injection 检测率 98%，幻觉推荐率降至 0%，零越权操作，推理安全校验耗时 < 1ms（不影响 P95 延迟）
- **简历话术**：*"设计四层安全防护体系。推理层采用确定性规则校验而非 LLM 二次判定——强制输出结构化溯源字段，通过 Python 内存级断言校验 item_id 是否存在于检索结果中（< 1ms），避免 Self-RAG 方案增加 500-800ms 串行 LLM 调用，与核心链路 P95 ~2.1s 目标兼容"*"

### 亮点 8：四级记忆系统 + Memory as Retrieval + 条件画像 + 背包上下文组装
- **S**：LLM 摘要丢失实体；全局用户画像跨品类均值化（30 万手表 + 15 元奶茶 = 无意义的"中等消费"）；固定比例 Token 预算在冷启动场景浪费严重（全新用户 40% 对话预算为空）
- **T**：设计分层记忆架构 + 动态 Token 预算的上下文组装器
- **A**：四级记忆——L1 工作记忆 / L2 对话记忆（L2a 滑动窗口 + L2b 摘要 + **L2c 向量检索**）/ **L3 条件画像**（品类隔离 + 场景隔离）/ L4 知识库。**上下文组装采用优先级背包算法**——7 级优先级队列（System Prompt > 当前输入 > L1 工作记忆 > 检索结果 > L2c 向量召回 > 滑动窗口 > 画像 > 历史摘要），按优先级装入 Token 预算，每个块有最小/典型两个尺寸，超预算时裁剪低优先级块。全新用户首次对话时，对话预算节省的 Token 全部让给检索结果；深度对话时 L2c 召回和画像自然占据更多预算
- **R**：实体召回率 45% → 92%，跨品类推荐准确率提升 35%，冷启动场景推荐精准度提升 40%（Token 从浪费的对话预算转移给检索结果）
- **简历话术**：*"设计四级记忆架构 + 优先级背包上下文组装器——L3 条件画像通过品类/场景隔离解决全局画像均值化问题，L2c 向量检索解决摘要丢失实体问题（实体召回率 45%→92%）。上下文组装采用 7 级优先级队列的背包算法替代固定比例分配，冷启动时对话预算节省的 Token 全部让给检索结果，推荐精准度提升 40%"*

### 亮点 9：LangGraph 原生 HITL（Human-in-the-Loop）
- **S**：敏感操作（下单/支付）需要用户确认，手写状态机实现挂起/恢复逻辑复杂、容易上下文丢失
- **T**：利用 LangGraph 原生的 interrupt_before + Checkpointer 机制实现安全拦截
- **A**：图定义中 `interrupt_before=["order"]`，Agent 执行到下单节点前自动挂起，Checkpointer 持久化完整 State；用户确认后通过 `Command(resume={...})` 恢复执行，State 零丢失。可插拔 Checkpointer 设计支持 Memory / SQLite / Redis 三种后端
- **R**：代码量减少 70%（相比手写状态机），状态一致性由框架级保证，支持 Time Travel 调试
- **简历话术**：*"利用 LangGraph 原生的 interrupt_before + Checkpointer 实现 Human-in-the-Loop，敏感操作自动挂起并持久化 State，用户确认后恢复执行，State 零丢失。相比手写状态机代码量减少 70%，且框架级保证状态一致性和崩溃恢复"*

### 亮点 10：Semantic Router 快慢系统 + 阈值标定
- **S**：每个请求都调用 LLM 意图分类，TTFB 高（~800ms），Token 浪费严重（简单意图也需要 ~200 tokens）
- **T**：设计"快慢系统"——轻量级语义路由处理简单意图，LLM 只处理模糊/复杂意图
- **A**：Semantic Router（BGE-M3 向量化 → 与意图样本库计算余弦相似度 → 置信度 > τ 直接路由，~5ms）+ LLM Fallback（置信度 < τ 时调用 LLM，~800ms）。**阈值标定**：构造正负样本对 → 计算余弦相似度分布 → F1 最优切分点确定 τ（BGE-M3 实测 τ 约 0.80-0.88，非直觉的 0.9）。配置化存储在 config.yaml，不硬编码。支持动态学习——LLM Fallback 的高置信度结果自动加入样本库
- **R**：70% 请求被快系统命中，加权平均 TTFB 从 800ms 降至 245ms，Token 消耗降低 70%
- **简历话术**：*"设计 Semantic Router 快慢系统——用 BGE-M3 向量相似度实现轻量级意图路由（~5ms），通过正负样本对的余弦相似度分布标定最优阈值 τ（F1 最大化），70% 的简单请求无需调用 LLM，加权平均 TTFB 从 800ms 降至 245ms，Token 消耗降低 70%"*

### 亮点 11：四层错误恢复与重试体系
- **S**：Agent 系统依赖 LLM、向量数据库、外部 API 等多个不稳定组件，任一环节瞬时故障都会导致整条链路失败，用户体验断裂
- **T**：设计覆盖 LLM / Tool / Memory / Frontend 四层的错误恢复与重试策略，区分静默错误与用户可见错误
- **A**：LLM 层（格式异常自动修复 + 429 指数退避 + 第 3 次切换备用模型）→ Tool 层（超时重试 + 缓存降级 + Qdrant 失败降级到 DB 查询）→ Memory 层（连接超时静默降级为无记忆模式，用户无感）→ 前端层（SSE 断流自动重连 + Checkpointer 断点恢复）。错误三级分类：静默重试（用户无感）/ 用户可见（有行动指引）/ 需用户介入
- **R**：瞬时故障自动恢复率 95%+，用户可见错误率降至 5% 以下，LLM 429 限流场景端到端延迟增加 < 2s
- **简历话术**：*"设计四层错误恢复体系：LLM 层实现格式自动修复 + 模型降级（重试 3 次后切换备用模型），Tool 层实现缓存降级（Qdrant 故障时降级到 DB 查询），Memory 层静默降级为无记忆模式（用户无感），前端层实现 SSE 断流自动重连。瞬时故障自动恢复率 95%+，用户可见错误率降至 5% 以下"*

### 亮点 12：全链路结构化日志 + 错误快速定位
- **S**：Agent 系统调用链长（7 个 LLM Agent + 4 个 Tool + 4 个 Memory 节点），出错时日志散落各处，定位一个错误需要翻多个日志文件，平均排查时间 10+ 分钟
- **T**：设计统一的结构化日志体系，实现 request_id / session_id 双 ID 关联，错误日志精确定位到模块+步骤
- **A**：JSON 结构化日志（每条含 timestamp / request_id / session_id / module / step / event / model / tool / input_length / duration_ms）→ 全链路 6 个埋点（意图识别 → 实体提取 → 上下文组装 → 检索 → 排序 → 生成）→ 错误日志增强（多 error_type / error_code / fallback_action / attempt / degraded 字段）→ request_id 串联单次请求全链路 / session_id 串联跨轮对话
- **R**：错误定位时间从 10+ 分钟降至 30 秒内，支持按 request_id 一键拉取完整调用链，按 session_id 回溯用户完整会话
- **简历话术**：*"设计全链路结构化日志体系——JSON 格式统一日志，request_id + session_id 双 ID 关联，覆盖 7 个 LLM Agent + 4 个 Tool + 4 个 Memory 节点共 6 个关键埋点。错误日志自动携带 error_type / module / step / fallback_action，出错时通过 request_id 一键拉取完整调用链，30 秒内定位根因"*
