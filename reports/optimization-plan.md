# ShopMesh 优化方案

> 版本: v1 · 日期: 2026-07-21
> 定位: 基于工程质量(面试视角)与用户体验(产品视角)双重诊断,给出按投入产出比排序的优化方案。

---

## 1. 现状诊断

项目工程量真实(约 1.8 万行 Python、118 次提交、双语言微服务),核心机制**确实接入**而非摆设(hooks / context compaction / error recovery 均挂在共享执行引擎 `specialized_agents._run_agent_loop`)。但存在两类结构性问题:

### 1.1 工程质量问题

| 编号 | 问题 | 证据 |
|------|------|------|
| E1 | **五套并行编排、四种执行 mode 全部存活**,无人能一眼说清主路径 | `shopping_graph` / `multi_agent_graph` / `orchestrator` / `dag_executor` / `dag_engine` 并存 |
| E2 | **死代码** | `src/graph/dag_engine.py`(生产 0 引用)、`src/graph/hello_world.py`(0 引用) |
| E3 | **默认生产路径(orchestrator DAG)零测试覆盖**,且历史有 "DAG Agent 循环修复" | `orchestrator.py` / `dag_executor.py` 无对应测试文件 |
| E4 | **测试数量与有效性背离**:486 个测试函数,但核心用户旅程(预算/品类过滤)无端到端断言 | `reports/problem.md` P0/P1/P2 均为漏测的核心链路 bug |
| E5 | **hooks 用模块级全局可变单例**,与"多租户隔离"卖点自相矛盾 | `src/graph/hooks.py` 的 `_HOOKS` 全局 dict |
| E6 | **过度设计**:5000 条 mock 数据的 demo 上了双语言 + Traefik + RabbitMQ(4 队列) + Celery + 双迁移 + 9 个 Docker 服务 | 组件复杂度与业务复杂度严重失衡 |
| E7 | 多处静默吞异常 | `src/auth/middleware.py:28/42`、`src/memory/memory_retriever.py` 多处 `pass` |

### 1.2 用户体验问题

| 编号 | 问题 | 影响 |
|------|------|------|
| U1 | **推荐数据是随机噪音**:清风(卫生纸)归"家居"卖 ¥2252、黛珂套装 ¥2515、价格与商品脱钩、**无商品图** | 信任第一秒崩塌 |
| U2 | **首字延迟高且静默**:preprocess → orchestrator → 多轮 ReAct 串行,首 token 前可能 10~20s 无任何进度反馈 | 用户以为卡死而离开 |
| U3 | **报错是死胡同**:"上下文过长,请重新开始对话" / "请稍后再试",无可见重试 | 一次即流失 |
| U4 | **刷新即失忆**:前端不拉历史(`ChatBox.tsx` 无历史加载/持久化),与后端四层记忆投入形成讽刺 | "它记得我"这个核心卖点用户感知不到 |
| U5 | **三个核心 bug 全在新用户必经路径上**(预算/品类/场景) | 首次体验直接判死刑 |
| U6 | **推荐理由未传导到前端**:后端有 `explainer.py`,但 ProductCard 未呈现"为什么推它" | 退化成普通搜索,丧失导购价值 |

---

## 2. 优化原则

1. **投入产出比优先**:用户会用脚投票的四件事——推荐准不准、快不快、错了怎么办、记不记得我——优先于任何架构美化。
2. **减法优于加法**:先收敛、删冗余,再谈新增。仓库整洁度是廉价的高信号。
3. **每修一个 bug,留一条回归测试**:把 `problem.md` 从"问题记录"升级为"回归防线"。
4. **诚实叙事**:主动暴露并反思过度设计,比被追问出来强。

---

## 3. 分阶段方案

### P0 — 让 demo "能看、可信"(1~2 天,ROI 最高)

#### P0-1 重建语义合理的商品目录 【对应 U1】
- **问题**:随机生成的目录导致推荐全是噪音。
- **方案**:重写 `scripts/generate_mock_products.py`:
  - 按品类维护合理的**价格区间字典**(护肤 50~800、数码 200~8000、食品 5~100…),价格从区间采样,不再全局随机。
  - 品牌与品类绑定白名单(清风→纸品/家居清洁,黛珂→护肤),杜绝错配。
  - `features` 从**品类相关特征池**采样(护肤:保湿/抗老/敏感肌;数码:续航/性能)。
  - 增加 `image_url` 字段(可用占位图服务或稳定 CDN 占位图)。
  - 去掉 `embedding_text` 中重复品牌名。
- **验收**:随机抽 20 条,品类/价格/特征人工判定"合理"≥ 18 条;前端能显示商品图。

#### P0-2 修复三个核心链路 bug + 补回归测试 【对应 U5/E4】
- **问题**:`problem.md` P0/P1/P2(预算过滤失效、品类过滤写反、场景不适配)。
- **方案**:确认修复已落地(problem.md 标注部分已修),为每条 bug 补**端到端断言测试**:
  - `test_budget_filter_e2e`:输入"预算 500 以内" → 断言所有结果 `final_price ≤ 500`。
  - `test_category_filter_e2e`:输入"帮我找化妆品" → 断言结果 category 均属护肤/美妆。
  - `test_scenario_fit_e2e`:输入"送女朋友生日礼物" → 断言结果不含奶茶/饮品品类。
- **验收**:三条测试通过并纳入 CI。

#### P0-3 分阶段进度反馈 + 报错可重试 【对应 U2/U3】
- **方案**:
  - 流式协议中在 preprocess / orchestrator / agent 各阶段推送轻量状态事件("正在理解需求""正在筛选商品"),前端展示。
  - 前端 `ChatBox.tsx` 报错气泡增加"重试"按钮,重发上一条。
  - 报错文案去"死胡同化":"上下文过长"改为**自动截断续跑**而非要求用户重开(后端 `_reactive_compact` 已有能力,补一条"已为你精简历史,继续"的用户可见提示)。
- **验收**:模拟 529 错误时用户看到重试按钮;长上下文不再强制清空对话。

---

### P1 — 架构收敛,一套主路径(2~3 天)【对应 E1/E2/E3】

#### P1-1 确定唯一主路径:`multi_agent_legacy`
- **决策**:保留确定性意图路由 → 每意图一个 ReAct agent(`multi_agent_graph.py` 的 legacy 分支)。
- **理由**:导购意图空间封闭已知(搜/推、详情/比价、澄清),确定性路由可预测、可测、易讲清;所有招牌优化都在共享的 `specialized_agents`,不随路由层删除而丢失。
- **动作**:
  - `src/api/chat.py` 的 `mode` 收敛为单一默认;移除 `workflow` / `agent` / 默认 orchestrator 分支。
  - 删除死代码:`dag_engine.py`、`hello_world.py`(连带 `test_t22`)。
  - `shopping_graph.py`、混合 `agent` 模式清理或明确标注废弃。
  - 修改 CLAUDE.md 中"原有函数不删不改"铁律——它是冗余的根源。

#### P1-2 orchestrator DAG 的去留
- **默认不启用**,若保留则标注 `mode=experimental` 并补齐:①端到端测试(复合意图拆解 + 环检测);②文档中给出"单 ReAct agent 做不了、非 DAG 不可"的真实 query 例证。举不出例证则直接删。

#### P1-3 修复 hooks 全局单例 【对应 E5】
- **方案**:将 `_HOOKS` 从模块级全局改为**每请求/每会话作用域**的 registry(随执行上下文创建与销毁),或至少提供请求结束时的清理钩子,避免跨请求污染。
- **验收**:并发两个请求注册不同 hook,互不影响的单元测试通过。

---

### P2 — 体验纵深与叙事(2~3 天)

- **P2-1 前端拉取历史会话** 【U4】:登录后加载会话列表 + 消息历史(后端已有持久化),让"它记得我"可感知。
- **P2-2 推荐理由呈现** 【U6】:ProductCard 展示 `explainer` 输出的一句话推荐理由 + 关键匹配点(价格/品类/场景命中)。
- **P2-3 静默异常治理** 【E7】:审查所有 `except: pass`,区分"可忽略"与"应告警",安全相关路径(auth middleware)至少记 warning。
- **P2-4 过度设计的诚实叙事**:在 README / 面试材料中主动写一段"架构反思"——早期引入双语言/RabbitMQ/双迁移属过度设计,复盘真实权衡与重来会怎么做。

## 4. 建议排期与里程碑

| 里程碑 | 内容 | 预估 |
|--------|------|------|
| M1 "能打动人的 demo" | P0-1 数据 + P0-2 核心 bug 回归 + P0-3 进度/重试 | 1~2 天 |
| M2 "经得起追问的代码" | P1-1 架构收敛 + P1-2 DAG 定性 + P1-3 hooks 隔离 | 2~3 天 |
| M3 "有产品纵深" | P2 全部 | 2~3 天 |

优先级理由:M1 的工作量远小于已写的架构,但对"用户是否愿意用第二次"是数量级提升;M2 直接决定面试现场"讲清主路径"的表现。

---

## 5. 明确不做 / 暂缓

- 不新增微服务组件、不扩大技术栈(与"减法优先"冲突)。
- 不为提升测试数量而写零散单测;只补护住核心旅程的端到端测试。
- Celery/RabbitMQ 队列拆分暂不动(现有能跑,非瓶颈),但在叙事中承认其对当前规模偏重。

---

## 6. 风险

- **数据重建**可能影响已构建的向量索引:P0-1 后需重跑 `scripts/build_index.py`,并回归检索相关测试。
- **架构删除**可能牵连隐式依赖:P1-1 删除前先跑反向引用扫描(`grep -rln`),逐文件确认。
- orchestrator 删除后,若简历/演示曾以"DAG 编排"为卖点,需同步更新对外材料口径。
